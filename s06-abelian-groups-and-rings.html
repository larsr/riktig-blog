Commutative structure: abelian groups and rings

A monoid is a set with an associative combining operation + and a do-nothing element 0 (so (a + b) + c == a + (b + c), 0 + a == a, a + 0 == a). A group adds undoing: a negation - a with (- a) + a == 0 and a + (- a) == 0, so every combination can be reversed. Nothing so far says the order of combination matters — and in a group it need not: composing two rotations one way generally differs from the other. This post is about the structures where order doesn’t matter, and about what a second operation buys once it does.

Throughout, == is the structure’s own notion of equality: an equivalence relation the carrier comes equipped with, not necessarily Coq’s built-in =. For the integers it is ordinary equality; in the next post it will be something else. And a =/= b is shorthand for ~ (a == b).

Each proof below is written as a chain. The line

calc x
  == y  { justification }
  == z  { justification }.

reads as x equals y by the fact in the first brace, which equals z by the fact in the second. Every brace names the single fact that justifies its step, and Coq checks the chain end to end, so the displayed calculation is the proof, not a comment alongside one.

The commutativity law

An abelian group is a group with one law added: combining is commutative, a + b == b + a. That is the whole definition, and the class says exactly that and nothing more — the group it extends is its first field:

Module AbGroup.
  Class AbGroup (A : Type) {eq : EqRel A} {zero : Zero A} {add : HasAdd A}
                {neg : HasNeg A} := {
    group    :: Group A;
    is_commutative :: Commutative A add;
  }.
  Hint Mode AbGroup ! - - - - : typeclass_instances.
  (* commutative has no terminating orientation; autorewrite with it loops. *)
  Hint Rewrite @commutative : comm_db.
End AbGroup.
Export AbGroup.

AbGroup.group holds a whole Group A — associativity, the two identity laws, the two undo laws, and the facts that + and - send equal inputs to equal outputs. AbGroup.is_commutative is the one new axiom, held as an instance of Commutative, the single-law class from Props.v whose method is commutative. Both fields are declared with :: rather than :, which registers them for instance search: with an abelian group in scope, everything proved about groups applies unchanged, and a proof can cite commutative to reorder a sum without naming where the law came from.

The comment on the last line is worth reading. Associativity and the identity laws each shrink or normalise a term, so a mechanical rewriting pass can apply them blindly; commutativity cannot — rewriting a + b to b + a and back never stops. So it goes into a database of its own, comm_db, which no blind pass uses.

A reshuffling kit

With commutativity in hand, sums of several terms can be permuted into any order. Two small lemmas do the local moves. Their statements:

Theorem add_swap_r : forall a b c : G, (a + b) + c == (a + c) + b.
Theorem add_swap_l : forall a b c : G, a + (b + c) == b + (a + c).

add_swap_r swaps the last two summands of a left-nested sum; add_swap_l swaps the first two of a right-nested one. Here is the left one in full. In words: reassociating to expose the front pair, swapping it, and reassociating back moves b ahead of a.

a+(b+c)=(a+b)+c{associativity}=(b+a)+c{commutativity}=b+(a+c){associativity}a + (b + c) \;=\; (a + b) + c \quad\{\text{associativity}\}\quad =\; (b + a) + c \quad\{\text{commutativity}\}\quad =\; b + (a + c) \quad\{\text{associativity}\}

Theorem add_swap_l : forall a b c : G, a + (b + c) == b + (a + c).
Proof.
  intros a b c.
  calc (a + (b + c))
    == ((a + b) + c)  { associative }
    == ((b + a) + c)  { (commutative a b) }
    == (b + (a + c))  { associative }.
Qed.

Step by step: associative reparenthesizes a + (b + c) as (a + b) + c; commutative a b, the new law applied to the pair a + b, turns it into (b + a) + c; associative reparenthesizes once more to land on b + (a + c).

The lemma worth its own name is the interchange law: two sums added together can be regrouped by pairing first-with-first and second-with-second.

(a+b)+(c+d)=a+(b+(c+d)){associativity}=a+(c+(b+d)){the swap lemma}=(a+c)+(b+d){associativity}\begin{aligned} (a + b) + (c + d) &= a + (b + (c + d)) &&\{\text{associativity}\}\\ &= a + (c + (b + d)) &&\{\text{the swap lemma}\}\\ &= (a + c) + (b + d) &&\{\text{associativity}\} \end{aligned}

Theorem add_interchange : forall a b c d : G,
  (a + b) + (c + d) == (a + c) + (b + d).
Proof.
  intros a b c d.
  calc ((a + b) + (c + d))
    == (a + (b + (c + d)))  { associative }
    == (a + (c + (b + d)))  { (add_swap_l b c d) }
    == ((a + c) + (b + d))  { associative }.
Qed.

The middle step is the only interesting one. associative first pulls the leading a out front, exposing the tail b + (c + d). Then add_swap_l b c d — the lemma just proved — swaps b past c inside that tail, rewriting b + (c + d) into c + (b + d). A final associative regroups a + (c + (b + d)) as (a + c) + (b + d). Four terms went in as (a b)(c d) and came out as (a c)(b d), with commutativity used exactly once, buried in add_swap_l.

Rings: a second operation

A ring keeps the abelian group under + and adds a second operation * with its own identity 1. Multiplication is associative and unital, and — the law that ties the two operations together — it distributes over addition: a * (b + c) == a * b + a * c, and the same on the right. Multiplication is not assumed commutative.

Module Ring.
  Class Ring (R : Type) {eq : EqRel R} {zero : Zero R} {add : HasAdd R}
             {neg : HasNeg R} {one : One R} {mult : HasMult R} := {
    abgroup    :: AbGroup R;
    mul_monoid :: @Monoid R eq one mult;
    is_left_distributive  :: LeftDistributive R R R mult;
    is_right_distributive :: RightDistributive R R R mult;
  }.
  Hint Mode Ring ! - - - - - - : typeclass_instances.
  Hint Rewrite @left_distributive @right_distributive : algebra_db.
End Ring.
Export Ring.

Two more operations join the parameters, a unit (One R) and a multiplication (HasMult R), and there are four fields. Ring.abgroup is the additive structure, held whole. Ring.mul_monoid is the interesting one: it is a Monoid — the same class the additive side is built from — but taken at the other operation and the other unit, which is what the explicit @Monoid R eq one mult spells out. Multiplication is associative and 1 is its two-sided identity because a monoid says so. A ring is two monoids on one carrier, one of them a commutative group, tied together by the last two fields: LeftDistributive R R R mult is a * (b + c) == a * b + a * c, and RightDistributive R R R mult is its mirror image. Multiplication is not assumed commutative.

Nor does the class separately demand that * respect ==; that obligation travels inside Ring.mul_monoid, whose magma field is exactly “multiplication sends equal inputs to equal outputs”. That is automatic when == is plain equality, but it is a real obligation when == is a coarser equivalence — which is the whole subject of the next post.

One name, two operations

Look back at the ring: it now has two associative operations on the same carrier (+ and *) and two identities (0 and 1). A proof about * will want to say “reassociate” and “use the identity” just as often as a proof about +. Watch how one short ring theorem does it. The fact — negating by multiplying by -1 — reads

(−1)⋅a=−(1⋅a){negation moves out of a product}=−a{multiplicative identity}(-1)\cdot a \;=\; -(1\cdot a) \quad\{\text{negation moves out of a product}\}\quad =\; -a \quad\{\text{multiplicative identity}\}

Theorem mul_neg1_l : forall a : R, (- (1)) * a == - a.
Proof.
  intros a.
  calc ((- (1)) * a)
    == (- (1 * a)) { (mul_neg_l 1 a) }
    == (- a)       { left_identity }.
Qed.

The first step uses mul_neg_l — the fact (- x) * y == - (x * y), that a negation can be pulled out of a product, proved earlier in the same file — to rewrite (-1) * a as - (1 * a). The second step names left_identity. But left_identity is the very name a monoid uses for 0 + a == a. How does the same name discharge 1 * a == a?

The answer is in Props.v, where the single-law classes live. A law is stated for an action, a function letting an element of one type act on an element of another, and for the unit of that action — never for one fixed operation:

Section LeftIdentityLaw.
  Context (A B : Type) {eqB : EqRel B} (action : A -> B -> B) (unit : A).
  Local Infix "·" := action (at level 40, left associativity).

  Class LeftIdentity := left_identity : forall x : B, unit · x == x.
End LeftIdentityLaw.

LeftIdentity A B action unit is the statement unit · x == x for a given action and unit (the equality rides along implicitly). The additive monoid inside Ring.abgroup supplies one instance of it, LeftIdentity R R add 0, as its own is_left_identity field. The multiplicative monoid Ring.mul_monoid supplies a second, LeftIdentity R R mult 1, on the same carrier and by the same field of the same class. Neither appears in the ring’s own text: there are two monoids, and each brings its identity laws with it.

So when a proof writes rewrite left_identity, Coq first reads the goal to see which operation is present — in mul_neg1_l the term is - (1 * a), which contains mult, not add — and only then searches for a LeftIdentity instance whose action matches. It finds the multiplicative one. A goal mentioning 0 + a would have matched the additive instance instead. One word resolved by the shape of the goal; likewise associative on a product means multiplicative associativity, associative on a sum means additive.

One law is pointedly absent. The multiplicative monoid supplies Associative, LeftIdentity and RightIdentity for *, and the two distributive fields tie * to +, but nothing anywhere supplies Commutative for * — multiplication in a general ring need not commute (square matrices are the standard counterexample), so rewrite commutative on a product finds no matching instance and simply fails. Adding that one instance is exactly what makes a ring a field, which is where the next post begins.

The integers are a ring

None of the above is worth anything until a real type satisfies it. The integers Z do: with == as ordinary equality, addition and multiplication from the standard library, and every law registered as its own instance — Z_mul_associative from Z.mul_assoc, Z_left_distributive from Z.mul_add_distr_l, and so on — the second monoid and the ring go up with almost nothing in them:

#[global] Instance Z_MulMagma : Magma Z mult := { Magma.equivalence := eq_equivalence }.
#[global] Instance Z_MulSemigroup : Semigroup Z mult := {}.
#[global] Instance Z_MulMonoid : @Monoid Z _ Z_One Z_Mult := {}.
#[global] Instance Z_Ring : Ring Z := {}.

The three lines before Z_Ring build the multiplicative monoid, the same three-step climb the additive one made earlier in the file, at Z.mul and 1 instead of Z.add and 0. Then the generic theory applies directly. For instance, mul_0_l — the ring theorem that 0⋅a=00 \cdot a = 0, proved once from distributivity for every ring — instantiates at Z:

Example z_mul_0_l : (0 * 7)%Z == 0.
Proof. exact (mul_0_l 7%Z). Qed.

No induction on integers, no case split on signs: the fact 0 * 7 == 0 for Z is the general ring lemma with R fixed to Z and a fixed to 7. The abstraction earns its keep the moment a second ring arrives and inherits the same body of theorems unchanged.
