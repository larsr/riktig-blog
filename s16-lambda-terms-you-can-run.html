Lambda terms you can run: de Bruijn, combinators, CPS

The lambda calculus is the smallest programming language that is still a programming language: variables, functions, application — three constructions, nothing else, Turing-complete. Formalizing it forces one famous question first.

Variables are not names — they are distances

Textbook lambda terms use names: λx. λy. x y. Names are treacherous. Is λx.x the same program as λy.y? (Yes — but now “same” needs a definition, α-equivalence.) Worse, substituting under a binder can capture a variable that just happened to share a name — the oldest bug in the book, and one that still bites real macro systems and compilers.

De Bruijn’s move: delete the names. A variable is a number — how many binders up is my λ?

λx.λy.xy⇝λ.λ.10\lambda x.\, \lambda y.\, x\, y \quad\rightsquigarrow\quad \lambda.\, \lambda.\, 1\; 0

0 means “the nearest binder”, 1 the one above it. In theories/Lambda/Syntax.v the whole language is three lines:

Inductive tm : Type :=
  | Var : nat -> tm
  | Abs : tm -> tm
  | App : tm -> tm -> tm.

What did the numbers buy us?

  • α-equivalence becomes =. λx.x and λy.y are both Abs (Var 0) — the same term, structurally. A whole equivalence relation evaporates.
  • Capture becomes arithmetic. Substitution must adjust indices when it walks under a binder (lift — shift free variables up) — a bookkeeping function with a two-line invariant, instead of a side-condition (“provided x is not free in N…”) that every proof must drag along. The file’s subst/lift are the textbook twenty lines, and a capture-avoidance Example checks the classic trap by reflexivity.

The price is the index arithmetic; the prize is that every proof about terms is structural induction with no naming side-conditions. Machines love it. (Humans get used to it.)

Terms you can run

A calculus is not a programming language until it runs. Lambda/Syntax.v gives evaluation twice, and proves the two agree:

  • a relation step : tm -> tm -> Prop — call-by-value β-reduction with its congruence rules; good for proofs;
  • a function step_fn : tm -> option tm — executable; good for running; with step_fn_sound and step_fn_complete tying them together, and a fuelled driver eval : nat -> tm -> tm on top (eval_sound : star t (eval fuel t)).

So inside Coq, Compute (eval 100 (App idt idt)) evaluates lambda code — and the examples in the file are discharged by reflexivity, which means the kernel itself runs the programs when it checks the file:

Example eval_id_id : eval 10 (App idt idt) = idt.
Proof. reflexivity. Qed.

(idt is the identity, Abs (Var 0).) reflexivity succeeds only because both sides compute to the same term. Evaluation is not something we argue about; it is something the kernel performs.

The same evaluator also runs outside Coq. theories/Lambda/Extract.v extracts eval, step_fn, cps and psi to Haskell, and the command-line tool in programs/lambda-eval wraps them in a parser and printer for ordinary named syntax:

$ ./programs/lambda-eval/lambda-eval "(\x. x x) (\y. y)"
\x. x

Two side trips, briefly: combinators and CPS

Two more classic transformations are built on the same datatype, and each gets a paragraph here and a file you can open.

Combinators (theories/Lambda/SKI.v): three closed combinators — Sfgx=fx(gx)S\,f\,g\,x = f\,x\,(g\,x), Kxy=xK\,x\,y = x, Ix=xI\,x = x — suffice to express every lambda term, so even variables can be deleted. The file defines the combinator language (CS, CK, CI, application @@) with an executable normalizer nf, and implements bracket abstraction — the algorithm that eliminates a variable — with the lemma babs_correct : forall t u, cstar (babs t @@ u) (csub u t): the abstracted term, applied, reduces to the substitution — β-reduction rebuilt without binders. The classic BB, CC, KK, WW basis is built from CS and CK as Bc, Cc and Wc, its specifications are Examples discharged by running the normalizer, and SfromBCW recovers SS from BB, CC and WW alone.

Continuation-passing style (theories/Lambda/CPS.v): the Fischer/Plotkin call-by-value CPS transform — control flow made into an explicit argument, the continuation — as one Fixpoint cps, plus the de Bruijn index accounting the textbook rules omit (the file’s header comment does that bookkeeping in public). One subtle point the proofs caught: a CPS program does not hand your continuation the original value but its CPS-converted twin (psi in the file), and the verification examples check exactly that by running both sides through the evaluator. The command-line tool shows the twin at the shell: (\x. x) (\y. y) evaluates to the identity directly, but CPS-transformed and handed the identity continuation it delivers the identity’s twin instead:

$ ./programs/lambda-eval/lambda-eval --cps "(\x. x) (\y. y)"
\x. \y. y x

Programs form a category

Objects are simple types; an arrow from AA to BB is a closed program of type A→BA \to B; composition is λx. g (f x); the identity arrow is λx. x. The category laws — id∘f=fid \circ f = f, associativity — then say that two programs are equal, and syntactically they are not: λx. (λy. y) (f x) is not the same term as f. They are equal only up to conversion, so the arrows have to be quotiented. theories/Impl/StlcCat.v does exactly that: simply-typed terms, intrinsically typed by context and result type, with a conv relation generated by congruence plus the three β and η instances the category laws need, and a Category instance whose hom-equality is that conversion. Equality of arrows is “programs behave alike”, and every construction that works in a category now works on syntax.

Next: conversion becomes a first-class rewriting relation — so that IFB b g h with b == TRUE rewrites to g in one step, partial evaluation as algebra. The lambda calculus stops being an object of study and becomes a tool.
