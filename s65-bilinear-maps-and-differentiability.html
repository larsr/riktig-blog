Bilinear maps, and why they’re automatically differentiable

A linear map between vector spaces over a field FF is a function that respects addition and scaling: f(u+u′)=f(u)+f(u′)f(u + u') = f(u) + f(u') and f(a⋅u)=a⋅f(u)f(a \cdot u) = a \cdot f(u), writing a⋅ua \cdot u for the scaling action of a scalar on a vector (the code writes it *:). Everything a linear map does is fixed by what it does to a basis, and it carries the zero vector to the zero vector. As always in this development, == is a setoid equality — a chosen equivalence relation every operation must respect — not equality of raw Coq terms.

This post is about the next step up: maps of two vector arguments that are linear in each one separately. They behave very differently from linear maps in one respect that turns out to matter for calculus, and the consequence is that establishing bilinearity is already enough to make such a map differentiable, with no further analysis to check by hand.

A bilinear map is linear in each slot separately

Linearity of a single function is stated first, as a property of a plain function — a typeclass indexed by the function f, so a lambda written at any use site can be shown linear without being packaged into anything:

Module Linear.
  Class Linear (F U V : Type)
      {eU : EqRel U} {aU : HasAdd U} {sU : HasScale F U}
      {eV : EqRel V} {aV : HasAdd V} {sV : HasScale F V}
      (f : U -> V) := {
    proper         :: Proper (equ ==> equ) f;
    is_additive    :: Additive U V add add f;
    is_homogeneous :: Homogeneous F U V scale (fun a => a) f;
  }.
End Linear.

Additive U V add add f is the reusable statement “f carries the first operation to the second”, i.e. f (x + y) == f x + f y; Homogeneous F U V scale (fun a => a) f is “f carries scaling to scaling, reweighting the scalar by the identity”, i.e. f (a *: x) == a *: f x. Both are named laws that other structures use too, so linearity is assembled from them rather than restating them.

Bilinearity is then that same property, twice, once per slot:

Module Bilinear.
  Class Bilinear (F U V W : Type)
      {Fe : EqRel F} {Fz : Zero F} {Fa : HasAdd F} {Fn : HasNeg F} {Fo : One F}
      {Fm : HasMult F} {Fi : HasInv F} {FF : Field F}
      {eU : EqRel U} {zU : Zero U} {aU : HasAdd U} {nU : HasNeg U} {sU : HasScale F U}
      {VU : VectorSpace F U}
      {eV : EqRel V} {zV : Zero V} {aV : HasAdd V} {nV : HasNeg V} {sV : HasScale F V}
      {VV : VectorSpace F V}
      {eW : EqRel W} {zW : Zero W} {aW : HasAdd W} {nW : HasNeg W} {sW : HasScale F W}
      {VW : VectorSpace F W}
      (b : U -> V -> W) := {
    proper :: Proper (equ ==> equ ==> equ) b;

    linear_l :: forall v : V, Linear F U W (fun u => b u v);
    linear_r :: forall u : U, Linear F V W (b u);
  }.
End Bilinear.

The long list of braced binders is the ambient algebra: F has to be a field, and each of U, V, W a vector space over it, before the laws can even be stated. The content is the last three lines, and it says literally what the English says. linear_l fixes the second argument at an arbitrary v and demands that fun u => b u v be linear; linear_r fixes the first at an arbitrary u and demands the same of b u. The proper field says bb respects the setoid equality in both arguments.

A bilinear map is then that property attached to a function, as a record:

Module BilinearMap.
  Class BilinearMap (F U V W : Type)
      {Fe : EqRel F} {Fz : Zero F} {Fa : HasAdd F} {Fn : HasNeg F} {Fo : One F}
      {Fm : HasMult F} {Fi : HasInv F} {FF : Field F}
      {eU : EqRel U} {zU : Zero U} {aU : HasAdd U} {nU : HasNeg U} {sU : HasScale F U}
      {VU : VectorSpace F U}
      {eV : EqRel V} {zV : Zero V} {aV : HasAdd V} {nV : HasNeg V} {sV : HasScale F V}
      {VV : VectorSpace F V}
      {eW : EqRel W} {zW : Zero W} {aW : HasAdd W} {nW : HasNeg W} {sW : HasScale F W}
      {VW : VectorSpace F W} := {
    map      : U -> V -> W;
    bilinear :: Bilinear F U V W map;
  }.
End BilinearMap.

Two fields: the function, and one proof that the function is bilinear. A bilinear map is an element — of a vector space of its own, as it happens — so no BilinearMap is ever registered as an instance for search to find; the laws themselves are the class above, and those search may look for freely. A Coercion declaration on BilinearMap.map means a BilinearMap named b can be applied directly, b u v.

Working with nested classes at the point of use is awkward, so the file also unfolds the two Linear fields back into the four flat equations a caller actually rewrites with. Each is a one-liner reading a law off the appropriate slot:

  Definition bilinear_left_additive (b : BilinearMap F U V W)
    : forall (u u' : U) (v : V), b (u + u') v == b u v + b u' v :=
    fun u u' v => additive (f := fun x => BilinearMap.map b x v) u u'.

Here additive is the projection of the Additive law, and the implicit argument f := fun x => BilinearMap.map b x v tells Coq which function’s additivity is wanted — the left slot with v frozen. The same shape gives bilinear_left_scale b, bilinear_right_additive b, bilinear_right_scale b, and bilinear_map_proper b.

Here is the one distinction to get right, because it is what makes bilinearity genuinely different from linearity. A bilinear map is not a linear map on the product space U×VU \times V. If it were, scaling the pair (u,v)(u,v) by aa would scale the output once, by aa. But scaling the pair scales both coordinates, and each scaling pulls out its own factor of aa:

b(a⋅u,a⋅v)=a⋅(a⋅b(u,v))=a2⋅b(u,v).b(a \cdot u,\; a \cdot v) = a \cdot \big(a \cdot b(u,v)\big) = a^2 \cdot b(u,v).

Scaling the input pair by aa scales the output by a2a^2, not by aa. Linear in each slot; quadratic on the pair. That single fact — that the output picks up the scalar twice — is exactly what will produce the quadratic remainder that makes the map differentiable.

One structure builds another: fixing a slot gives a linear map

Before the calculus, one clean algebraic consequence. If you hold the first argument of a bilinear map fixed at some uu, what remains is a function of one vector — and it is a genuine LinearMap, because bilinear_right_additive and bilinear_right_scale are precisely the two linear-map laws for that function. The file packages exactly this:

  Definition bilinear_map_appl (u : U) : LinearMap F V W :=
    linear_map_from_laws
      (fun v : V => b u v)
      (bilinear_map_appl_proper u)
      (bilinear_right_additive b u)
      (fun (a : F) (v : V) => bilinear_right_scale b a u v).

linear_map_from_laws is the builder that takes a function and its three laws and returns the record. Read the three proof arguments: the additivity law of the new linear map is bilinear_right_additive b u — the right-slot additivity of bb with the first argument frozen at uu — and its scaling law is bilinear_right_scale b a u v, the right-slot scaling law, likewise frozen. Fixing a slot of a bilinear map hands you a linear map for free, with no new proof obligations: the laws you need are the laws you already have.

This immediately buys a fact that would otherwise take its own argument. A linear map sends the zero vector to the zero vector; so a bilinear map, fed the zero vector in either slot, returns zero.

The claim: bu0=0b\,u\,0 = 0 for every uu.

The blackboard argument is one sentence: v↦buvv \mapsto b\,u\,v is a linear map (that is bilinear_map_appl u), and every linear map kills zero (that is linear_map_zero), so bu0=0b\,u\,0 = 0. The Coq is that sentence, verbatim:

  Theorem bilinear_map_zero_r : forall u : U, b u 0 == 0.
  Proof.
    intros u.
    exact (linear_map_zero (bilinear_map_appl u)).
  Qed.

linear_map_zero (bilinear_map_appl u) is the general “linear maps send 00 to 00” lemma instantiated at the linear map you get by freezing the first slot at uu. Nothing about bilinearity had to be re-proved: the linear-map machinery applies the moment bilinear_map_appl exhibits the fixed-slot map as linear.

Bilinearity forces differentiability

Now the reason bilinear maps are worth isolating. Recall what it means for a function ff to be differentiable at a point aa with derivative a bounded linear map LL: the error left after the linear approximation, f(a+h)−f(a)−Lhf(a+h) - f(a) - L\,h, must shrink faster than ‖h‖\lVert h\rVert itself. Precisely, for every ε>0\varepsilon > 0 there is a δ>0\delta > 0 such that ‖f(a+h)−f(a)−Lh‖≤ε‖h‖\lVert f(a+h) - f(a) - L\,h\rVert \le \varepsilon\,\lVert h\rVert whenever ‖h‖<δ\lVert h\rVert < \delta. The derivative is the best linear map through the point; differentiability is the promise that the leftover is negligible next to hh.

Take a bilinear map B:U×V→WB : U \times V \to W, regarded as a function of the single pair argument p=(u,v)p = (u,v), and a base point (u0,v0)(u_0, v_0). The claimed derivative is the map sending a displacement (du,dv)(du, dv) to Bduv0+Bu0dvB\,du\,v_0 + B\,u_0\,dv — vary the first slot alone, plus vary the second slot alone:

  Definition bilinear_deriv_fun (p : U * V) : W :=
    B (fst p) v0 + B u0 (snd p).

This is a LinearMap F (U * V) W (its additivity and scaling laws follow from BB’s slot-wise laws — the file proves bilinear_deriv_add and bilinear_deriv_scale for exactly this). The question is whether it is the derivative: is the leftover quadratically small?

The remainder is a single cross term

The blackboard argument expands B(u0+du,v0+dv)B(u_0 + du,\; v_0 + dv) by bilinearity — right slot first, then each half in the left slot:

B(u0+du,v0+dv)=Bu0v0+Bduv0+Bu0dv+Bdudv.B(u_0 + du,\; v_0 + dv) = B\,u_0\,v_0 \;+\; B\,du\,v_0 \;+\; B\,u_0\,dv \;+\; B\,du\,dv.

Four terms. The first is the value Bu0v0=B(u0,v0)B\,u_0\,v_0 = B(u_0,v_0). The middle two are precisely the claimed linear approximation Bduv0+Bu0dvB\,du\,v_0 + B\,u_0\,dv. Subtract off the value and the linear part, and exactly one term survives — the cross term BdudvB\,du\,dv, the one where both displacements act. That is the quadratic term the “scales twice” observation predicts:

  Lemma bilinear_remainder_eq : forall (du : U) (dv : V),
    B (u0 + du) (v0 + dv) + - (B u0 v0 + (B du v0 + B u0 dv)) == B du dv.
  Proof.
    intros du dv.
    calc (B (u0 + du) (v0 + dv) + - (B u0 v0 + (B du v0 + B u0 dv)))
      == ((B (u0 + du) v0 + B (u0 + du) dv)
            + - (B u0 v0 + (B du v0 + B u0 dv)))
        { bilinear_right_additive }
      == (((B u0 v0 + B du v0) + B (u0 + du) dv)
            + - (B u0 v0 + (B du v0 + B u0 dv)))
        { bilinear_left_additive }
      == (((B u0 v0 + B du v0) + (B u0 dv + B du dv))
            + - (B u0 v0 + (B du v0 + B u0 dv)))
        { bilinear_left_additive }
      == (B du dv)
        { four_term_cancel }.
  Qed.

Reading the chain: bilinear_right_additive B (u0+du) v0 dv splits the right slot, turning B(u0+du)(v0+dv)B(u_0+du)(v_0+dv) into B(u0+du)v0+B(u0+du)dvB(u_0+du)\,v_0 + B(u_0+du)\,dv. The two bilinear_left_additive steps then split the left slot of each piece, producing all four terms. four_term_cancel is a pure abelian-group rearrangement: (a+b+c+d)−(a+(b+c))=d(a + b + c + d) - (a + (b + c)) = d. What is left is BdudvB\,du\,dv, and nothing else.

The cross term is quadratically small

So differentiability comes down to: is ‖Bdudv‖\lVert B\,du\,dv\rVert small compared to ‖(du,dv)‖\lVert (du,dv)\rVert? On the product space we measure a pair by the sum norm, ‖(du,dv)‖=‖du‖+‖dv‖\lVert (du,dv)\rVert = \lVert du\rVert + \lVert dv\rVert; call this ‖h‖\lVert h\rVert. Assume BB is bounded — there is a constant C≥0C \ge 0 with ‖Buv‖≤C‖u‖‖v‖\lVert B\,u\,v\rVert \le C\,\lVert u\rVert\, \lVert v\rVert always (a hypothesis, exactly as for linear maps, not a field of the record). Since ‖du‖\lVert du\rVert and ‖dv‖\lVert dv\rVert are each at most their sum ‖h‖\lVert h\rVert,

‖Bdudv‖≤C‖du‖‖dv‖≤C‖h‖‖h‖.\lVert B\,du\,dv\rVert \le C\,\lVert du\rVert\,\lVert dv\rVert \le C\,\lVert h\rVert\,\lVert h\rVert.

This is quadratic in ‖h‖\lVert h\rVert, and that is why it is negligible: for a target ε\varepsilon, choosing the neighbourhood radius δ=ε⋅(1+C)−1\delta = \varepsilon \cdot (1 + C)^{-1} forces C‖h‖≤εC\,\lVert h\rVert \le \varepsilon whenever ‖h‖<δ\lVert h\rVert < \delta, which turns the quadratic bound C‖h‖⋅‖h‖C\,\lVert h\rVert \cdot \lVert h\rVert into the required ε⋅‖h‖\varepsilon \cdot \lVert h\rVert. The file proves exactly this padding estimate:

  Lemma bilinear_remainder_bound : forall C : F, 0 <= C ->
    (forall (u : U) (v : V), ‖ B u v ‖ <= C * ‖ u ‖ * ‖ v ‖) ->
    forall eps : F, 0 < eps ->
    forall (du : U) (dv : V),
      ‖ du ‖ + ‖ dv ‖ < eps * inv (1 + C) ->
      ‖ B du dv ‖ <= eps * (‖ du ‖ + ‖ dv ‖).

The proof is a chain of monotonicity steps: bound ‖Bdudv‖\lVert B\,du\,dv\rVert by C‖du‖‖dv‖C\,\lVert du\rVert\,\lVert dv\rVert (the boundedness hypothesis), raise each factor ‖du‖,‖dv‖\lVert du\rVert, \lVert dv\rVert to the sum ‖du‖+‖dv‖\lVert du\rVert + \lVert dv\rVert, and finally use ‖h‖<ε(1+C)−1\lVert h\rVert < \varepsilon\,(1+C)^{-1} to collapse one surviving factor of C‖h‖C\,\lVert h\rVert to ε\varepsilon. This is the one place where bilinearity demands genuine analysis rather than algebra — precisely because the remainder is the product of two small quantities, not the sum of two small quantities.

The theorem

Both halves assemble into the theorem. Differentiability in this development is a pair: the derivative is a bounded linear map, and the ε\varepsilon/δ\delta remainder estimate holds. The proof supplies one half from bilinear_deriv_bounded and the other from the two lemmas above:

  Theorem bilinear_is_deriv : bm_bounded B ->
    is_deriv (fun p : U * V => B (fst p) (snd p)) (u0, v0) bilinear_deriv_lm.
  Proof.
    intros Hbb.
    split.
    - exact (bilinear_deriv_bounded Hbb).
    - destruct Hbb as [C [HC HCb]].
      intros eps Heps.
      exists (eps * inv (1 + C)).
      split.
      + exact (pad_div_pos eps C Heps HC).
      + intros [du dv] Hh.
        rewrite (prod_norm_at du dv) in Hh.
        simpl.
        unfold LinearMap.map, bilinear_deriv_lm, bilinear_deriv_fun; simpl.
        calc (‖ B (u0 + du) (v0 + dv) + - (B u0 v0 + (B du v0 + B u0 dv)) ‖)
          == (‖ B du dv ‖)
          == (eps * ‖ (du, dv) ‖).
        * apply eq_le. apply vnorm_proper. exact (bilinear_remainder_eq du dv).
        * rewrite (prod_norm_at du dv).
          exact (bilinear_remainder_bound C HC HCb eps Heps du dv Hh).
  Qed.

Reading it: split breaks differentiability into its two obligations. The first, bilinear_deriv_bounded Hbb, discharges “the derivative is a bounded linear map.” For the second, unpacking the boundedness witness gives the constant CC; then for a given eps the proof offers the radius δ=ε(1+C)−1\delta = \varepsilon\,(1+C)^{-1} with exists (eps * inv (1 + C)), shows it is positive (pad_div_pos — a positive numerator over a padded divisor is positive whatever C is), and takes an arbitrary displacement (du, dv) inside that radius. The closing calc chain is the two-step estimate laid out above: the norm of the leftover equals the norm of the cross term BdudvB\,du\,dv (that is bilinear_remainder_eq, applied under NormedSpace.vnorm_proper since equal vectors have equal norms), and that cross term is bounded by ε‖(du,dv)‖\varepsilon\,\lVert (du,dv)\rVert (that is bilinear_remainder_bound). prod_norm_at is where the sum norm ‖(du,dv)‖=‖du‖+‖dv‖\lVert (du,dv)\rVert = \lVert du\rVert + \lVert dv\rVert meets the shape the bound was proved in — an equation cited, not an instance unfolded.

So bilinearity is not merely compatible with differentiability — it forces it. Once a map is shown linear in each slot and bounded, its derivative is written down explicitly (vary one slot at a time, add), and the error is a single cross term whose norm is a product of two small things, hence quadratically small. No limits are computed by hand; the one genuine analysis step is the padding estimate, and it is the same estimate for every bilinear map at once.
