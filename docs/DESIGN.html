Design & style

How code and proofs are written in this repo (riktig). What we aim for is in VISION.md; this document is the style contract.

Program style

  1. Top level reads in the domain’s language. A program is a pipeline of named stages (fetch url >>= decodeJson >>= traverse_ process) readable as a description of what it does.

  2. Program-as-data. Arg parsing produces one value — a Plan — that defines what the program does; a small interpreter executes it. No behavior decided by scattered if-statements mid-flow. (The free-monad DSLs are the formalized version of this same pattern.)

  3. Errors are values; policy floats to the top. Lower layers never fudge (no "" for a missing file). They return explicit failures; what to do about them (skip / retry / abort / default) is a field of the Plan, set at the top. Parse, don’t validate.

  4. No layer leakage. Lower layers are named in their own vocabulary and stay parametrically polymorphic: a fetcher maps URL → bytes and cannot know upper datatypes — parametricity as architectural enforcement (the same trick that stops MemProg programs from forging addresses).

  5. Short and clear; find the abstraction line. Every component is the most general program of its kind — a cache knows nothing about auth, an auth fetcher nothing about LLMs; expiry is part of what “cache” means, not a special case above it. Use-case knowledge exists only at the composition point, which then reads as one sentence (“get the cookie from the cache at xyz or else request-and-cache it; invoke the llm”). Boilerplate is a smell that a concept wasn’t factored out — refactor the concept, don’t elaborate the handler.

  6. Recursive Coq programs: code once, as a plain lambda term; obligations after. (Adopted 2026-07-15; the model is theories/Programs/Merge.v.) The governing principle: do not stray from lambda calculus. A program is a plain CIC term — fun, match, Fix, application — that you could print and recognize as what you wrote; machinery that elaborates the source into something else (Program Fixpoint’s sigma-packed _func wrappers and subset types, the Equations plugin’s clause compilation) is out, however convenient. Concretely: a recursive program that is not structurally recursive is one refine whose body is a single ordinary ML-looking term: uncurry ∘ Fix (well_founded_ltof _ <measure>) turns the curried arguments into the one tuple the measure needs, the tuple is matched ONCE with flat, first-match clauses under a single p = x convoy, conditions are written if dec (..) then .. else .., and every termination hole is discharged by one combined tactic line after the term ((subst p; unfold ltof; simpl; abstract lia)) — abstract, because lia’s generated proof terms get very large, and in a Defined (transparent) definition they would otherwise sit inside the program term itself and be re-typechecked at every unfolding; abstract hides them behind an opaque constant and keeps the lambda term small. The clause equations are then derived from the definition via Fix_eq, in the model file’s four-line shape:

    rewrite Fix_eq.
- destruct dec; f_equal.
- intros [[|x x'] [|y y']] f g H; auto.
  destruct dec; rewrite !H; f_equal.

    — the equation branch is destruct dec; f_equal, and the extensionality premise closes by the pointwise rewrite !H, so no functional_extensionality: the model file’s Print Assumptions is closed under the global context. The dec-vs-boolean bridge is a general lemma (lem1 there), not per-proof gymnastics. Reasoning about the program goes through the derived equations, never by unfolding the fixpoint — the same rule as 3’s “never unfold interp”. (Program Fixpoint achieves code-once too but its generated obligations capture the recursive function inside subset proofs, making the derived equations need a le_unique detour — the Fix form above is both shorter and cleaner.)

    Two further rules, made explicit 2026-07-16. No auxiliary function that is the function: defining f_aux that differs from f only in argument order (to put the decreasing argument where Fix wants it) and then wrapping f a b := f_aux b a states the program twice and doubles the derived equations; the tupled uncurry ∘ Fix form with the right measure (snd for gcd) writes the program once in its conventional argument order. A worker with a genuinely different signature (a reparameterization the recursion needs, not a shuffle) is not covered by this rule, but prefer recursing on the caller’s own arguments with a measure when possible. No fuel: termination is always by a well-founded measure, never by a fuel : nat argument threaded through the recursion — fuel changes the function’s type, pollutes every equation with “enough fuel” side conditions, and proves nothing about the algorithm. Never use fuel for a computation we know terminates — sorting a list, manipulating a tree, structural compilation. Fuel has exactly one legitimate home: an interpreter or evaluator running arbitrary code that might genuinely loop forever, where the point is to run for a while and see whether an answer or an error comes back (Lambda/’s step-bounded runners, the Memprog machine interpreters). There the partiality is a fact about the language being interpreted, not about our algorithm — and a per-program “this much fuel suffices” lemma is what restores the honest statement for programs that do terminate. The older refine (Fix ...) files (Programs/BinarySearch.v, Programs/Quicksort.v, Programs/MergeSort.v) predate the tupled form and stand as written until their scheduled rewrite; Programs/Gcd.v was converted 2026-07-16 (aux eliminated, and with it the file’s functional_extensionality import — the flat motive closes Fix_eq’s premise pointwise).

Proof style

(The worked-out model is enter-docker/math; the discipline mirrors lean-test/DESIGN.md.)

  1. Four layers. Ops.v — operational typeclasses, one per symbol, no laws. Props.v — single-law property classes (Associative, LeftIdentity, …). Interface/ — structure classes over the Ops vocabulary (the ops are implicit class parameters, not fields), each law a :: field naming the Props.v class that states it, never a forall written out a second time (rule 7) — plus the bundles that state what a map or a choice must satisfy (LinearMap, BilinearMap, Basis, Determinant), which are specs too, just ones carrying a value. Rules 7–9 below say how all of these are written.

    A property is a class; a Record is data. The dividing line is whether instance search should ever go looking. A property that a proof might need supplied — a map is additive, homogeneous, linear, bilinear, alternating; a pair of maps is a two-sided inverse — is a Class over a plain function, so a lambda written at a use site can be shown to have it without being packaged into anything first. A Record survives only where a map is an element of something: the hom space Theory/HomVS.v builds, the category Impl/VectCat.v builds, the witness an isomorphism carries, a chosen basis. Search must never hunt for one of those, so they get no Hint Mode and no module. Each such record is then the function (or the pair of maps) plus one :: field holding its property, and a *_from_laws constructor takes the law proofs positionally. The old field names come back as plain definitions, so a spelling the tree already used keeps working. Theory/ — lemmas derived generically via Section/Context, including the abstract structure-transfer constructions (a function space, product, Hom-space, or subspace inherits structure — instances with no data structure of their own). Impl/ — data-structure realizations of the abstract structures, so one can compute with them: Z, Q, matrices as Fin m -> Fin n -> F, coefficient lists, the complex record — the mathematical analogue of Programs/, and usable by programs. A file does exactly one of these jobs. (Refined 2026-07-16: the transfer constructions Theory/Pointwise.v, Theory/FieldVS.v, Theory/HomVS.v, Theory/ProdVS.v, Theory/UnitVS.v, Theory/Subspace.v moved from Impl/ to Theory/ under this criterion — they are abstract theory, not representations; the test for Impl/ is “does this file give you something to compute with”. The field-as-its-own-vector-space instances live in Interface/VectorSpace.v itself, beside the class: Field_Scale must be visible, definitionally, wherever a *: x is written at a field carrier, and Theory/FieldVS.v keeps the compiled check that the transfer really is an instance.)

    Fourth pattern, blessed 2026-07-08: a Theory/ file may define the canonical generic algorithm for the construction it studies — bigop/bigopF in Theory/BigOp.v, Gram-Schmidt’s gram_schmidt_aux/gram_schmidt in Theory/GramSchmidt.v — when the algorithm has no separate abstract spec worth writing (there is no “Summation” or “Orthogonalization” Interface for it to satisfy) and is itself generic over an existing Interface (Monoid, PosInner), not tied to one concrete carrier. The algorithm is the theory being studied. New operational vocabulary still belongs in Interface/; concrete data-structure representations still belong in Impl/. (The 2026-07-08 wording also excluded instance-minting from Theory/; the 2026-07-16 refinement above supersedes that — abstract structure-transfer instances are Theory content, and only computable representations are Impl content.)

    Fifth pattern, blessed 2026-07-08, narrowed 2026-07-16: a Theory/ file may import a specific Impl/ file when its content is theory about that named representation itself. The original motivating cases (Theory/Hom.v over Theory/HomVS.v/Theory/FieldVS.v, Theory/VSIso.v over Theory/ProdVS.v/Theory/UnitVS.v/Theory/Pointwise.v) dissolved when those constructions moved to Theory/ — they are now ordinary Theory-imports-Theory. What remains under this pattern: theory about a genuine representation, e.g. Theory/MatRep.v, Theory/Trace.v, Theory/MatMulBilinear.v, and Theory/Determinant.v importing Impl/Matrix.v (their theorems are ABOUT the matrix representation), and Theory/Merge.v importing Programs/Merge.v (properties of a named program). The test is unchanged: could the file’s theorems be stated without naming that specific representation? Rule 6 still forbids the OTHER direction and the accidental case — a generic algorithm over an abstract Interface must still not import a concrete representation’s lemmas it doesn’t need to name.

    Standing exception, recorded 2026-07-13: three directories sit deliberately outside the four-layer split altogether — theories/Channel/, theories/Lambda/, and theories/Programs/. Each is a self-contained track about concrete objects-of-study (traces and protocols; a calculus; executable example programs) rather than abstract structures-with-many-instances, so the Ops/Props/Interface/Theory/Impl decomposition would add layers without adding instances; internally each file keeps spec, theory and implementation content in clearly ordered, usually explicitly numbered sections. The Channel/ and Lambda/ exemption was examined and recorded in docs/LINALG-ROADMAP.md’s Wave L8 section (the 2026-07-08 audit); Programs/’s is that decidability reaches the programs as plain Coq = and stdlib sumbool — nothing from the algebra tower touches the code itself. Decidable itself is a full Interface/Theory/Impl family as of 2026-07-16: Interface/Decidable.v (the Decidable/EqDec classes and the dec vocabulary), Theory/Decidable.v (closure under the connectives, equality transported to lists and pairs, dec_if_bool), Impl/Decidable.v (nat and bool). theories/Examples/ is a fourth such track — compiled usage examples pinned from the blog, depending on everything, depended on by nothing. Two clarifications recorded 2026-07-16: theories/Programs/ holds the implementations of algorithms and their derived clause equations; properties proved ABOUT a program (permutation, sortedness, correctness) go in theories/Theory/ next to the rest of the proved mathematics (Theory/Merge.v about Programs/Merge.v is the model). And theories/Lib/ holds plain Coq conveniences that are part of no mathematical structure — the calc chains (Lib/Calc.v) and measure induction (Lib/MeasureInd.v, a placeholder until a proper theory of induction replaces it); they may be used by any track and depend on nothing.

  2. Operational typeclasses carry notation. HasAdd/Zero/EqRel give +, 0, == for any instance; proofs read like textbook derivations (rewrite <- associative; rewrite right_inverse; rewrite right_identity; reflexivity).

  3. Setoid discipline. Work over an equivalence == with Equivalence and Proper instances so rewrite works everywhere — including under binds, once program equivalence === exists for the memory DSL. Never prove a program property by unfold interp; simpl; if you are unfolding an interpreter, the missing piece is an equivalence lemma.

  4. Each lemma is the most general statement of its fact (rule 5 above, applied to proofs). Arithmetic side-conditions get factored into named reusable lemmas rather than inline lia everywhere.

  5. Honest incompleteness. No Axiom. An Admitted must carry a comment with a proof sketch — a roadmap, not a shrug. Specs owe an equivalence proof to a canonical formulation (a structural Sorted must be proven equivalent to pairwise Ordered).

  6. Import discipline. Dependencies point one direction: implementations import theories, theories import structures, never the reverse; an algorithm written against an abstract interface must not import a concrete instance’s lemmas.

    Require the deepest name, not the chain (decided 2026-08-01). Each Interface/ file re-exports its parent, so

    From Riktig.Interface Require Export VectorSpace.

    already carries Field, Ring, AbGroup, Group, Monoid, Semigroup, Magma, Props and Ops. Naming the ancestors as well is clutter, and it obscures which structure the file is actually written against. Theory/ chains the same way — Theory.AbGroup carries Theory.Group. Require Import S imports everything S exports, so an Import of an already-exported name is always redundant; an Export is redundant only when the name is re-exported by something this file also exports.

    Two things stop a require being redundant, and neither is visible in the dependency graph:

    • Position. The implying require must be processed no later than the one it would replace. Theory/KleisliIso.v states its classes above its Impl.OptionMonad require, so its Interface.Monad has to stay where it is.
    • Deliberate shadowing. A repeated require can exist purely to be imported last, so its names win. Programs/ABNF/Parser.v re-requires Theory.Monad after Ast so that the monadic map shadows List.map. Such a line carries a comment saying so.

  7. Structure classes are assembled from law classes: one substructure field, one field per law, no equation written twice (decided 2026-07-31, superseding the 2026-07-25 flat-field design and its Section Laws membership instances). Every law in the tree is a class in Props.v stated over a plain operation. A structure class names those laws; it does not restate them. The whole of Interface/Group.v, minus its Require Export line:

    Module Group.
  Class Group (G : Type) {eq : EqRel G} {zero : Zero G}
              {add : HasAdd G} {neg : HasNeg G} := {
    monoid    :: Monoid G;
    neg_proper :: Proper (equ ==> equ) neg;
    is_left_inverse  :: LeftInverse G add neg 0;
    is_right_inverse :: RightInverse G add neg 0;
  }.
  Hint Mode Group ! - - - - : typeclass_instances.
  Hint Rewrite @left_inverse @right_inverse : algebra_db.
End Group.
Export Group.

    That is the entire file. There is no Section Laws, no is_Monoid, no from_laws, and no forall x y z : G, … anywhere: monoid :: is the membership, and LeftInverse G add neg 0 is the law. A structure gets longer only by acquiring more laws, never by copying its parent’s.

    Operations are implicit op-class binders. {eq : EqRel G}, {add : HasAdd G} and friends come from Ops.v, so a use site writes `{Group G} and the operations arrive with it. The two exceptions are Magma and Semigroup, whose op is an explicit (op : BinOp M) parameter because one carrier has several — a ring is a Semigroup twice over, once at each operation — and search cannot pick for you.

    Export, not Notation. The module wrapper keeps the law names (left_inverse, left_distributive) from colliding as definitions; Export Group. immediately after End Group. makes the class reachable as bare Group. No file anywhere writes Group.Group, and an interface that Require Exports its parent hands the whole chain onward: a file that wants rings writes From Riktig.Interface Require Import Ring. and has Ops, Props, Magma, Semigroup, Monoid, Group and AbGroup in scope with it. Each Interface file therefore Require Exports exactly its immediate parent and nothing else.

    Laws are heterogeneous where the mathematics is. Props.v states associativity and the two identities about an action act : A -> B -> B, so Associative M M add add is a monoid law and Associative F V smul mult is the scalar-action law — the same class, and rewrite associative closes both. LeftDistributive/RightDistributive are heterogeneous the same way. A monoid is a monoid acting on itself; the code says so rather than a comment. Commutative is the one law that cannot be heterogenized (op a b == op b a needs one type) and stays single-carrier.

    Guarded laws take the domain as a predicate. An inverse need not invert everything: LeftInverseOn T P op inv unit requires P a before op (inv a) a == unit. Field uses it at the guard nonzero F, which is what lets a division ring be a Field minus mul_commutes rather than a separate development. LeftInverse is the total case, and left_inverse_defined_everywhere presents every total inverse as a guarded one, so a theorem proved about LeftInverseOn also holds of every group. invertible is the other stock guard, for a monoid whose inverse is only defined on its invertible elements.

    Guarded laws stay out of algebra_db: autorewrite has no way to discharge the P a side condition.

    Respect laws are Proper fields. Magma carries Equivalence eq and Proper (equ ==> equ ==> equ) op, so every structure above it has both by inheritance and only the new operations need a Proper field of their own (neg_proper in Group, inv_proper in Field). Because these are stated over the raw binder rather than a projection, Ops.v marks its operation classes Typeclasses Transparent, and each Interface file that introduces one of its own repeats the line (HasLe, HasAbs in Order.v; HasNorm in Norm.v; HasOlt, HasOle in DecTotalOrder.v). Without it Equivalence eq never matches a goal spelled Equivalence (@equ T Te) and rewriting fails with “equ is not a declared transitive relation”.

    Hint Mode forces the carrier and nothing else. Write Hint Mode Group ! - - - - : typeclass_instances. inside the module. The ! on the carrier is what stops search unifying ?M := ?X -> ?M' against a pointwise instance and recursing until coqc runs out of memory. A ! anywhere else is a bug: reaching a substructure means solving Field F … ?inv with the operation still an evar, and a mode that refuses it makes every inherited instance unreachable — measured 2026-07-31, when `Hint Mode Field ! - - - - -

    • !leftRing F,Associative F addandCommutative F addall unresolvable from ``{Field F} `, whileField F recip` itself resolved fine.

    Two positions deserve - on purpose beyond that rule. The unit of an identity or inverse law (LeftIdentity, RightIdentity, LeftInverse, LeftInverseOn, …): a use site’s left-hand side pins the carrier and the operation, and which element is the unit is what the instance answers. Forcing it also trips a Coq 8.20 bug — a ! in that position makes a plain rewrite (left_inverse_on a Ha) raise Anomaly "Uncaught exception Not_found". And the operation of Magma/Semigroup, because an Equivalence eq lookup carries no operation to unify against; every Magma on a carrier answers it identically, and op_proper lookups pin op from the goal.

    A guard predicate must be named, not unfolded. A caller holding Ha : a =/= 0 cannot write left_inverse_on a Ha: elaboration solves ?P a to an anonymous lambda, convertible with nonzero F but not equal to it, and instance search matches heads rather than converting. Either state the hypothesis as nonzero F a, or pass the guard — left_inverse_on (P := nonzero F) a Ha.

    Why the operations are parameters and not fields (measured 2026-07-30). Take a bundled Monoid carrying m_equ, m_zero, m_add as record fields, a bundled Group carrying its own g_equ, g_zero, g_add, g_neg, and a Group_is_Monoid instance that repackages the Group’s fields. In a goal written in the Group’s operations, the Monoid theorem shunt : forall a b c, m_equ (m_add (m_add (m_add a m_zero) b) c) (m_add a (m_add b c)) is unusable by any matching tactic: apply shunt, rewrite shunt, rewrite m_idr, and even rewrite (m_idr (Monoid := Group_is_Monoid G _) a) all fail, because matching must line m_add ?inst a m_zero up with g_add a g_zero and the two agree only after the instance is unfolded and the projection reduced. exact (shunt G a b c) does succeed — exact type-checks up to conversion — so the statements are the same proposition and only matching is lost. Nothing repairs the matching: Typeclasses Transparent on all six operation projections, Hint Unfold for them in both core and typeclass_instances, a priority-0 duplicate of the membership instance, and unfold Group_is_Monoid in * before the rewrite each leave all three tactics failing. With the operations as shared parameters the same rewrites go through first-order at any distance in the tower.

    What needs a locality attribute, and what does not (measured 2026-07-31, then corrected 2026-08-01 after a first answer proved wrong).

    A :: class field needs nothing. It defaults to #[export], and since every structure module ends with Export X., a Require Import of the file activates it. Verified with a two-file test: an unannotated :: field resolves fine through Require Import, and fails only under a bare Require, which the tree never does for Riktig modules (all 39 bare requires are Coq stdlib).

    An Instance at top level is written bare (decided 2026-08-02, replacing the earlier blanket #[global]): Instance name {binders} : C := …, no attribute, no wrapping Section — the default #[export] locality survives every Require Export chain, and where every field is found by search the body is {} (Interface/VectorSpace.v’s field-over-itself instances are the model: four one-liners). What #[export] does not survive is a plain Import link in the middle of a chain: Examples/GettingStarted.v imports Impl/FinVec.v, which reaches Theory/Pointwise.v by Import, and an unattributed PW_EqRel made EqRel (Fin.t 2 -> Q) unresolvable three files away. #[global] is therefore a per-case exception, like #[local]: it stays only where a full build proves the default insufficient (the Pointwise instances are the standing example), and adding or removing the attribute needs a full build either way. Inside a Section an unattributed Instance dies at End; the narrowest surviving form is #[export]. Prefer hoisting to top level with explicit binders when the Section holds nothing else; a Section whose Context is shared by several declarations earns its keep. A spelled-out record literal stays where its fields name plain lemmas that search cannot find — the ScaleLaws bundles built from a file’s own lemmas are the standing example; {} is for instances whose every field is itself an instance, like the two-field VectorSpace bundles.

    Hint, Hint Mode, Hint Rewrite, Typeclasses Transparent and Arguments at top level are already global; 197 redundant attributes were removed from those.

    #[local] Instance is the deliberate exception, and it is not an oversight where it appears. Programs/Memprog/Quicksort.v’s Z_lt_decidable/Z_le_decidable would shadow what Impl/Decidable.v owns if they escaped the file, and Lambda/CalcExamples.v’s cstar_Transitive exists only so calc can chain cstar in that one file. An instance that would be wrong to export is declared #[local] and says why.

    The trap worth naming: a file compiling after the attribute is removed proves nothing. Locality governs what downstream files see, so only a full build tests it. The first version of this rule claimed top-level Instance was redundant on exactly that bad evidence.

    Coq’s :: syntax deliberately does not default to global: the older :> auto-registered every such field, and the Coq team removed that default because it let instances leak into every importing file silently. There is no setting that restores it. (:> still appears where it is a coercion on a data record’s underlying function — bm_fun, mf_fun, lm_fun, determinant_form — not an instance declaration.)

    Hint Rewrite on a law projection needs a monomorphic wrapper. Because the identity and associativity laws are stated over an action, their projections carry two type parameters that autorewrite cannot discharge, so registering @left_identity directly makes the database silently fail to fire. Theory/Group.v and Theory/Ring.v therefore export add_left_identity, add_right_identity, add_left_inverse, add_right_inverse, mul_left_identity and mul_right_identity, and the grp, su3 and su3fin databases register those. Skipping this is not a compile error — it leaves goals open wherever the tactic was relied on.

    Binders. Law fields need no forall at all now, but a Section that opens a structure still annotates its carriers, and exactly one bare generalizing binder per shared scalar: writing `{Field F} twice puts two independent copies of EqRel F, Zero F, HasAdd F, … in scope, and a hypothesis about the first neither exacts nor rewrites into a goal about the second (checked 2026-07-30). A section over several carriers opens with one generalizing binder for the scalar and then writes each further carrier’s operations out, named by initial, followed by its structure hypothesis as a plain binder. Theory/Bilinear.v is the model:

    Context {F U V W : Type} `{FF : Field F}.
Context {eU : EqRel U} {zU : Zero U} {aU : HasAdd U} {nU : HasNeg U} {sU : HasScale F U}.
Context {VU : VectorSpace F U}.

  8. Naming: full descriptive words, no abbreviations (decided 2026-07-20, superseding the abbreviated style — mon_idl, grp_invl, ip_add_l — used before that date; since 2026-07-25 the structure-name prefix lives in the module path, not the identifier). A structure’s law fields read as English inside the module — left_inverse, not left_inverse; mul_associative, not mulA — and the structure’s name arrives by qualification (Group.left_inverse, Ring.mul_associative), never as a group_/ring_ prefix baked into the field name. Because the module already carries the structure’s name, the declarations inside it need no prefix either:

    • The substructure field is the weaker structure’s name in lower case — monoid :: Monoid G in Group, abgroup :: AbGroup R in Ring, ring :: Ring F in Field, semigroup, magma, group. ScaleLaws is the exception that proves the rule: it is a mixin rather than a level of the tower, so both VectorSpace and GeometricAlgebra name it scaling :: ScaleLaws F V.
    • A field naming a law is is_ plus the Props.v class in snake case — is_left_inverse :: LeftInverse G add neg 0, is_associative, is_left_distributive. The is_ says the field asserts a property rather than holding one. Exception (recorded 2026-08-02): when the law class is instantiated away from its namesake operations, so that the class name alone would misstate the law, the field names what it says instead — Exp.add_to_mul :: Additive F F add mult fn (sums to products; is_additive would claim the wrong equation) and Alternative.fail_left_identity/fail_right_identity (which element is the identity).
    • The respect law is named after its operation: neg_proper, inv_proper, scale_proper, op_proper, abs_proper, quad_proper, bind_proper.

    There are no from_parts smart constructors: a structure is built by giving its fields, and the fields are law classes that instance search already knows how to find. The bridges into Props.v are anonymous — an instance nothing ever names does not need a name. None of this touches the generic property-class field names themselves (Props.v’s associative, left_identity, right_identity, left_inverse, right_inverse, commutative, left_distributive, right_distributive, … stay as they are — those are the short, uniform vocabulary every structure’s laws resolve through inside a calc step’s brace, by design).

    Since 2026-07-25 every module-wrapped structure class in Interface/ carries no prefix — the last of them lost theirs the way Interface/Order.v did, ordered_field_le_total becoming OrderedField.le_total. Three kinds of declaration are deliberately not wrapped:

    • Operational and definitional classes — Decidable, EqDec, DecEq, and the Has… family (HasAdd, HasScale, HasInner, HasLe, HasAbs, HasOlt, HasOle, HasNorm, HasBind, HasReturn, HasFail, HasAlt). Their method name IS the vocabulary (add, scale, le, dec), so there is nothing to de-prefix.
    • The property classes of Props.v — Associative, Commutative, LeftIdentity, RightIdentity, LeftInverse, RightInverse, LeftDistributive, RightDistributive, Unique, Injective. Each is a single law about an operation or a map, and its one field is the short uniform word the calc braces resolve through, so there is no structure name to strip.
    • The thin bundles LinearMap, BilinearMap, MultilinearForm, Determinant, Basis, and the three isomorphism records — they carry a value rather than laws about a carrier, so instance search must never hunt for one (no module, no Hint Mode on the record). Their compatibility projections keep the record’s name as a prefix, since nothing qualifies them: bilinear_left_additive, multilinear_form_scale, determinant_basis_normalization. Because a record’s parameters are not class parameters, each of these files follows the record with one Arguments line per field, listing the whole operation chain as implicit, so downstream code writes basis_vec B and lm_fun f rather than the twenty-argument form.

    ScaleLaws (Interface/VectorSpace.v) — the scaling mixin shared by VectorSpace and GeometricAlgebra — is module-wrapped like the rest. Its respect field keeps scale in the identifier (scale_proper) because the module name says only that these are laws, not which operation they are about; its four law fields take the is_ form and name the Props.v class, with the scaling action supplied as the argument that says which operation is meant:

    is_left_distributive  :: LeftDistributive F V V Vs;
is_right_distributive :: RightDistributive F V V Vs;
is_associative        :: Associative F V Vs mult;
is_left_identity      :: LeftIdentity F V Vs 1;

    Both VectorSpace and GeometricAlgebra pick the mixin up as a single scaling :: ScaleLaws F V field rather than restating it.

    Interface/Category.v is wrapped but keeps hom, id and comp as fields — it is parameterised over the object type, not over operation classes — and exposes them through Notation hom := Category.hom, cat_id, comp, so call sites read unqualified. Interface/GeometricAlgebra.v uses the same device for its one operational field, Notation ga_vec := GeometricAlgebra.vec.

  9. A class states only the laws it adds (decided 2026-07-31, reversing the 2026-07-20 restate-everything rule). Where a class strengthens a structure on the same carrier, it carries the weaker structure as its first :: field and states nothing that field already implies. Counted in Interface/: Magma 2 fields, Semigroup 2, Monoid 3, Group 4, AbGroup 2, Ring 4, Field 5. A reader who wants the full law set of a Field follows four one-screen files, each of which says exactly what that level contributes; nobody maintains a fifteen-line copy of the ring axioms in three places, and a concrete instance proves each law once as an instance of the corresponding Props.v class rather than supplying a field per level.

    What is required ambiently rather than inherited. A class whose own laws are about a different vocabulary layered on top takes the structure as a generalizing binder in the class header instead of a substructure field, and states only its own laws. OrderedField requires `{Field F}; FormallyReal requires the same; InnerProductSpace requires `{VectorSpace F V}; NormedSpace requires `{OrderedField F} and a plain {VS : VectorSpace F V} binder — plain, because generalizing it would insert a second Field F beside the one OrderedField F already supplies.

    Class field lists are column-aligned (the :: and the type lined up down the block) so the field names read as a table, not a ladder of different-length lines — matched to whatever the longest name in that particular class requires, not a fixed column across the tree.

  10. Equational proofs are calc chains, not raw rewrite scripts (standing rule, restated 2026-07-20 after an audit found real gaps — Theory/Log.v’s log_mono among them). A proof whose content is “a chain of equal or related terms, each justified by one law” is written with Lib/Calc.v’s calc notation (or one of its named/mixed/calcrw forms, per that file’s header), never as a bare sequence of three or more rewrites that leave the intermediate terms invisible. A 1–2 step rewrite, a case split, or a decision procedure is not required to become a calc chain — the rule targets exactly the shape Rule 2 above already describes (rewrite <- associative; rewrite right_inverse; rewrite right_identity; reflexivity, which itself should now be read as the desugared form a calc chain compiles to, not the form to write by hand). docs/TODO.md tracks any file found still using the raw form.

  11. Plain commutative-ring identities go to ring, not to a calc chain (recorded 2026-07-30). Theory/Ring.v’s ring_theory_of_Ring builds the ring_theory record that Coq’s setoid-ring plugin wants out of any Ring R, given one extra fact — commutativity of multiplication, which Ring does not require in general (End V in Theory/HomVS.v is noncommutative) and which a Field supplies unconditionally as commutative. So over an abstract field, one line inside a Section registers the tactic on the tower’s own +/*/-/0/1/==:

    Section AbstractFieldRing.
  Context {F : Type} `{Field.Field F}.
  Add Ring F_ring : (ring_theory_of_Ring (R := F) commutative).

  Lemma binomial : forall a b : F,
    (a + b) * (a + b) == a * a + (1 + 1) * (a * b) + b * b.
  Proof. intros a b. ring. Qed.
End AbstractFieldRing.

    The registration is per-Section: Add Ring captures the exact operation terms in scope, and a section-local F does not survive End, so Theory/Ring.v deliberately does not register the record itself and each section that wants the tactic re-registers it under its own name — Impl/Cliff2.v six times, Impl/Cliff13.v four, Theory/Maxwell.v once. Theory/Field.v’s field_theory_of_Field is the same construction one level up (its extra fields are exactly Field.nontrivial and Field.mul_left_inverse); Impl/Qf.v runs Add Field Q_field from it and Impl/Zr.v runs Add Ring Z_ring from ring_theory_of_Ring, so ring and field work on goals stated in the tower’s notation, not only on raw Qplus/Z.add.

    What this buys, and what it costs to miss: in Impl/Cliff13.v the two distributivity laws of a 16-dimensional Clifford algebra are repeat split followed by simpl; ring on each of the 16 component goals, where the alternative is a hand-written 16-term shuffle lemma per law. Impl/Cliff3.v registers Add Ring in each of its ten sections, one registration per section because the command is section-local. Rule 10 therefore does not ask for a chain where ring is the single justification; a chain is for steps where naming the law is what makes the proof readable.

  12. Comments explain Coq; the mathematics goes in a blog post (decided 2026-07-31). A .v file carries only what a reader cannot get from the code itself: a Coq-ism, a workaround for a tool limitation, or why an absence is deliberate. It does not carry a header explaining what the theory is, what it is for, how its pieces behave, or what was decided and when. That material is a blog post per file — tutorial language, pretty notation, linking into the coqdoc so the source reads as trivial once the post has been read. docs/BLOG-SYLLABUS.md tracks which file has which post.

    The lever that makes this possible is rule 8: when names are full descriptive words, most comments become unnecessary because the code already says what they said. Props.v carries zero comments and is readable, because LeftInverseOn T defined_on op inverse unit needs no paragraph explaining that the inverse is guarded.

    Measured on 2026-07-31: Interface/ went from 848 comment lines in 1953 (43%) to 3 in 1112. The three survivors are the model for what earns a comment —

    • Decidable.v: why no Hint Mode is declared (Impl/Orders.v resolves dec _ with the proposition still undetermined, which a strict mode would forbid);
    • AbGroup.v: why commutative is in comm_db and not algebra_db (no terminating orientation, so autorewrite loops);
    • Magma.v: why its operation is an explicit parameter (one carrier has several).

    Each states a fact about the system, not about the mathematics. Theory/SU3Algebra.v, at 242 comment lines in 919, is the next file to bring into line.

    A comment never says what changed, what it used to be, or what the author just did — that is what git is for.

  13. A lemma lives in the theory of the weakest structure that states it (decided 2026-07-31; the placement half of rule 4, which already requires the most general statement). A fact whose statement mentions only +, - and 0 is a group fact and belongs in Theory/Group.v, however it was first needed. Writing it inside the specialised file that wanted it hides it from every other caller and inflates that file with material nobody would look for there.

    Theory/SU3Algebra.v is the cautionary example: of its 93 lemmas at least ten mention no su(3) vocabulary at all — negAA_plus_A_plus_A, AA_plus_negA_plus_negA and negA_plus_3A are group facts; neg_add_rev is neg_add reversed; distr3_l/distr3_r/scale3_l/scale3_r are ring facts; mul3_comm12 and field_self_neg_zero are field facts.

    Before writing such a lemma at all, try the general tactic: rule 11’s Add Ring is available over any abstract field, and a plain commutative-ring identity should be discharged by ring rather than named, proved and carried.

The DesignExample.v sandbox

DesignExample.v sits at the repository root. It is untracked, absent from _CoqProject and from the Makefile, and is built by hand with coqc -Q theories Riktig DesignExample.v. Nothing in it is a statement about theories/. It is a place to try structure-class shapes end to end — operations, laws, a concrete carrier, and a Clifford algebra on top — before any of it is proposed for the library.

It is under active edit — it changed three times in the ten minutes this section took to write (2026-07-30) — so line references into it go stale immediately, and its build state is a thing to check rather than assume: the 09:30 version stopped with No applicable tactic, the 09:41 version compiled clean. Nothing in it counts as demonstrated on a version that does not build.

Two of its patterns became the library’s, on 2026-07-30: the Section Laws inside each module, opened with a bare generalizing binder (grep -rn "Section Laws" theories/ now returns 8), and respect laws as :: Proper fields inside the class (31 such fields across Interface/). Rule 7 documents both. Two patterns remain the sandbox’s alone:

  • A module-wrapped bundle of a carrier’s operations, used at binder sites. The sandbox has Module VectorOps — a class with fields eq, zero, add, neg, scale, followed by one #[global] Existing Instances eq zero add neg scale. — and binds `{VectorOps.VectorOps F U} where the library writes the five binders out. grep -rn "Existing Instances" theories/ returns nothing.
  • A Module Type Signature and a functor Clifford.Algebra (Sig : Signature), so one construction yields Cl(2,0), Cl(3,0), Cl(1,3) and Cl(0,1) at different signatures. grep -rn "Module Type" theories/ returns nothing: the library writes one Impl/ file per algebra (Cliff2.v, Cliff3.v, Cliff13.v, CliffordFin.v).

Two things the sandbox and the library agree on, in different spellings. The sandbox’s Group.from_Monoid is the same idea as the library’s substructure field: build the stronger structure from a proof of the weaker one plus the new laws, rather than restating what the carrier has already proved. The library needs no constructor for it — monoid :: Monoid G is the proof of the weaker structure, and the remaining fields are the new laws. And VectorOps exists in the sandbox for the reason Rule 7’s one-bare-binder paragraph gives, as its own comment says — “the scalar appears only as a type, so binding a second carrier over it introduces no second field”. The library reaches the same place by writing the binders out and generalizing the scalar exactly once.
