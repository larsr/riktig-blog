I have three more tasks i want to add.

[ ] 1. for the lambda calculus i want to define a function that converts a lambda term, to one where all function calls are made with let-bound variables as arguments, i.e defined in let bindings higher up. this is done with a set of conversions like defunctionalisation, making functions take all argumentes, i.e not have any bound variables inside them, and instead have a context argument, etc. the conversion should be done as recursive rewrite on the nodes of the lambda term tree. finally the term should be a 1-to-1 mapping into another type that enforces that all function calls are in the form we just said - variable for function and variables for the arguments. then it is easy to convert the program to machine code. note, there are a few functions that will actually need to exist, like reading /writinga word/byte from an address, add words/bytes, etc. but all of the lambdas defined in the original program should disappear by this transform.

(Investigated 2026-07-20, verdict independently reproduced: do
NOT land. `Additive`/`ScaleCommutes` classes work only for the
"right-slot" shape where `f` is already syntactically applied in
the goal (`inner u`, `lm_fun h`, `mult a`) — bare `rewrite
additive` there is bounded (one candidate, no backtracking) and
genuinely shortens four real proof sites (GramSchmidt.v's
`orthogonal_sub`, InnerGeometry.v's `orthogonal_scale_r`,
Adjoint.v's `isometry_preserves_inner`, plus LinearMap/Ring/
VectorSpace analogues). But Lars's two motivating laws
(`ip_add_l`, `ip_scale_l`) are "left-slot" — `f` would have to be
the INVENTED lambda `fun x => ⟨x,w⟩`, and Coq's `rewrite` builds
`f` from the goal's literal application head (`inner`, arity 2),
never eta-expanding to find a shared one-argument `f` across two
occurrences; `setoid_rewrite` doesn't either. Worse: `rewrite
additive` against a genuinely unregistered function does not
fail cleanly under this tree's mandatory Hint Mode — it throws
`Anomaly "Uncaught exception Not_found"` (Coq 8.20.1, reproduced
independently). Dropping the Hint Mode avoids the anomaly but
lets `apply` silently unify `f` with a bogus lambda over a
dangling evar — exactly the failure Hint Mode exists to prevent
elsewhere in this tree. Nothing landed; the scratchpad has the
full test suite (Verify1–10.v) if this is revisited.)
