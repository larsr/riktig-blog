Plan — the big sum by its laws, everywhere

Written 2026-08-18. Nothing here is started. The shape below was validated end to end in Coq before the plan was written; the working skeleton is reproduced in full under “The design”, so whoever executes this does not have to rediscover it.

The request (Lars, verbatim, 2026-08-18)

“Theory/BigOp.v now imports Impl/BigopFold.v, so Theory-files-importing-Impl goes 14 -> 15. It needs the instance because bigopI and bigop are definitions at the fold.” explain. in theory one should only interact with the operations via the laws, never with computation.

The rule is right and the tree does not keep it. The import was the symptom; the disease is that a concrete fold_right is named inside specifications.

What is actually wrong

bigopI is Structure/BigOp.v’s fun f => bigop_list f enum and bigop is Lib/BigopList.v’s bigop_list f (seq 0 n), both at Lib’s fold_right. Measured on main at fae3037b:

site what it says
Structure/BigOp.v:84 BigopSum’s law bigopI_sum is stated with the concrete bigopI
Structure/Graded.v:61 grade_complete is stated with the concrete bigop
Structure/Series.v:45,59 two laws, same
Structure/GradedProducts.v:37,40 the wedge and dot laws, same
Theory/BigOp.v 17 sections, 61 lemmas, 992 of 1563 lines, all about the concrete bigopI

Four specifications name a computation. That is the part that matters: a law mentioning fold_right cannot be satisfied by a second sum, so nothing it implies transfers, which is what the abstraction was for.

The design, validated

Compiles as written (checked 2026-08-18 against Ops, Props, Structure.Monoid, Structure.Fin).

(* Structure: the laws, operation as a parameter. *)
Class BigOpL (M : Type) {Me : EqRel M} {Mz : Zero M} {Ma : HasAdd M}
    (bl : forall J : Type, (J -> M) -> list J -> M) := {
  bl_nil  : forall (J : Type) (f : J -> M), bl J f nil == 0;
  bl_cons : forall (J : Type) (f : J -> M) (j : J) (l : list J),
    bl J f (j :: l) == f j + bl J f l;
}.

(* Theory: a section over ANY lawful operation, with its own sum at the
   enumeration and its own defining equation. *)
Section AbstractIndexed.
  Context {M : Type} `{MM : Monoid M}.
  Context {bl : forall J : Type, (J -> M) -> list J -> M} {BL : BigOpL M bl}.
  Arguments bl {J}.
  Context {n : nat} {I : Type} {eI : EqRel I} {Ieq : EquDec I}
    {FI : FinIndex n I}.
  Let bigopI (f : I -> M) : M := bl f enum.
  Lemma bigopI_def : forall f : I -> M, bigopI f == bl f (enum : list I).
  Proof. intros f. reflexivity. Qed.
  (* ... the section's lemmas, unchanged ... *)
End AbstractIndexed.

(* Impl: the concrete term and its instance. *)
Instance fold_BigOpL {M : Type} `{Monoid M} : BigOpL M (@fold_sum M _ _).
Proof. split; intros; reflexivity. Qed.

(* Downstream: the abstract lemma applies to the concrete sum. *)
exact (bigopI_nil_case (bl := @fold_sum M _ _) f He).

Three things this settles, each of which cost a probe to learn:

  1. Let plus a section-local bigopI_def keeps every existing proof. The 30 citations of bigopI_def in Theory/BigOp.v resolve to the local one and need no editing — provided the global bigopI_def is gone (see obstacle 1).
  2. enum needs its index annotated in any statement where the operation is a parameter: bl f (enum : list I), not bl f enum. With a concrete operation the index was pinned; with a parameter it is not, and the error is an unresolved ?eI : EqRel ?I a long way from the cause.
  3. Downstream citations name the operation: (bl := @fold_sum M _ _). Unification does not always find it.

Obstacles, and why the order below is the order

  1. Coq refuses to let a section shadow the global bigopI_def. So the per-section local equation only works once the global one is deleted. That forces step 2 before step 3.
  2. Deleting the global bigopI drags in Structure/BigOp.v, because BigopSum’s law names it. This is how the Structure-level problem was found, and it means the Structure work cannot be deferred.

Order of work

Each step ends green (make -f CoqMakefile -j8, then make linkcheck, which now includes homecheck). Commit per step.

  1. Structure/BigOp.v — BigopSum takes the sum as a parameter. Small: one class, one law.
  2. Move the concrete bigopI to Impl/BigopFold.v, beside the fold instance, and delete the global bigopI_def from Theory/BigOp.v. Expect breakage in the 22 files that use bigopI to compute; they should import Impl/BigopFold.v and are otherwise unchanged.
  3. Theory/BigOp.v, 17 sections — each gains the four lines above. Carriers differ per section (M, G, R, F, V, and X M for the pointwise one); the Context line’s type must match. Proofs are untouched. This is the bulk: budget most of the day here.
  4. Structure/Graded.v, Structure/Series.v, Structure/GradedProducts.v — each takes the nat-bounded sum as a parameter. Highest risk: the GA and analysis tracks are built on these three, so every instance and every section mentioning them moves. Do this last, and expect the same Hint Mode arity errors that the operation-class removals produced (Hint Mode X ... has N arguments while the mode declares N-1).
  5. Drop Impl.BigopFold from Theory/BigOp.v — it should be unnecessary by then. If it is not, step 3 is incomplete.

Verification

  • Theory/ files importing Impl/ returns to 14 (it is 15 today, and the extra one is exactly this).
  • grep -n "bigop" theories/Structure/*.v shows no law naming a concrete sum.
  • No new axioms: Print Assumptions on bigopI_swap, mat_mul_assoc, grade_complete’s consumers.
  • The beauty gate Lars set for the first bigop change applies again: compare before/after on a class head, a section header and a proof, and stop if the answer is uglier.

What this is not

Not a second operation, not a rename, and not a change to any lemma statement. Every statement in Theory/BigOp.v should read exactly as it does now; what changes is what it is a statement about.
