The evaluator leaves the building

A program written inside a proof assistant is in an awkward place. It lives there because that is where you can prove things about it, while the machine meant to run it is somewhere else — a machine that has no notion of a proof and would not know what to do with one if you handed it over. Getting the program out is a translation, and two things make that translation more than a change of punctuation.

The first is that proofs and programs are written in the same notation. A term you think of as a program may have evidence embedded in it — that an index is in range, that a list is nonempty — put there to satisfy the type checker and contributing nothing to the answer. If that evidence survives the translation it costs time and space in the running program, so the translation has to recognize which subterms are evidence and drop them.

The second is that the representation which makes a proof easy is rarely the one that makes a program fast. A natural number defined as “zero, or the successor of a natural number” is ideal for induction and hopeless as a counter: adding two of them walks a linked list. So the translation must also be free to replace a datatype with a different one the target language implements better — without disturbing what was proved about the original.

Coq’s extraction mechanism does both: it discards the proof content and emits ordinary functional code, here Haskell. This post takes one small verified program through it — an evaluator for the lambda calculus — out to a command you can type at a shell, and keeps track of which part of the result a theorem still says something about.

The program: one call-by-value step at a time

A lambda term is a variable, an abstraction \x. body, or an application f a. Variables are de Bruijn indices, a number counting the enclosing \s out to the binder, so the identity \x. x is Abs (Var 0):

Inductive tm : Type :=
  | Var : nat -> tm
  | Abs : tm -> tm
  | App : tm -> tm -> tm.

Evaluation is call-by-value and left-to-right: in f a, first reduce f to a function, then a to a value, then substitute. A value is anything that is not a pending application — an abstraction, or a variable stuck for want of an argument — which is one line to decide:

Definition is_value (t : tm) : bool :=
  match t with
  | App _ _ => false
  | _ => true
  end.

One reduction step is then a total function returning None when there is nothing left to do. subst 0 a b replaces the outermost bound variable of b by a, and option_map pushes a step performed on a subterm back into the surrounding application:

Fixpoint step_fn (t : tm) : option tm :=
  match t with
  | App f a =>
      if is_value f then
        if is_value a then
          match f with
          | Abs b => Some (subst 0 a b)
          | _ => None
          end
        else option_map (App f) (step_fn a)
      else option_map (fun f' => App f' a) (step_fn f)
  | _ => None
  end.

Running a term means iterating that until it returns None. But iterating “until” is not something a total function may say: the term (\x. x x) (\x. x x) steps forever, and a Coq function that chased it would never return. The driver therefore takes a step budget and stops when the budget is spent:

Fixpoint eval (fuel : nat) (t : tm) : tm :=
  match fuel with
  | O => t
  | S fuel' =>
      match step_fn t with
      | Some t' => eval fuel' t'
      | None => t
      end
  end.

The budget is there because the language being interpreted has terms with no normal form, not because the iteration is hard to justify. That distinction matters for what can be proved next: eval cannot promise to deliver a value, so the theorem has to say something weaker, and say it exactly.

What the answer means

The weaker thing is reachability. Write star for the reflexive-transitive closure of the step relation step — zero or more genuine call-by-value steps:

Inductive star : tm -> tm -> Prop :=
  | star_refl : forall t, star t t
  | star_step : forall t u v, step t u -> star u v -> star t v.

Then whatever eval hands back, for any budget at all, is a term the input really does reduce to:

∀n,t.t→*eval(n,t)\forall n,\, t.\qquad t \;\longrightarrow^{*}\; \mathrm{eval}(n,t)

On the blackboard the argument is an induction on the budget nn. With n=0n = 0 the driver returns tt itself and the chain is empty. With n+1n + 1, either there is no step available, and again the answer is tt; or there is one, t→t′t \longrightarrow t', and the induction hypothesis gives t′→*eval(n,t′)t' \longrightarrow^{*} \mathrm{eval}(n, t'), so prefixing the single step yields the chain from tt. The one thing the argument needs from outside is that the executable step_fn only ever reports steps the relation step agrees with:

Lemma step_fn_sound : forall t t', step_fn t = Some t' -> step t t'.

The Coq proof is that induction, four lines long:

Lemma eval_sound : forall fuel t, star t (eval fuel t).
Proof.
  induction fuel as [| fuel IH]; intros t; simpl.
  - constructor.
  - destruct (step_fn t) as [t'|] eqn:H.
    + econstructor.
      { apply step_fn_sound; exact H. }
      { apply IH. }
    + constructor.
Qed.

induction fuel splits the two cases, and simpl unfolds eval in each. Zero fuel: the goal is star t t, which is star_refl, so constructor closes it. Successor fuel: destruct on step_fn t asks whether a step exists, remembering the answer as H. When it does, econstructor picks star_step, leaving the single step — supplied by step_fn_sound applied to H — and the rest of the chain, which is the induction hypothesis IH at t'. When it does not, eval returns t and star_refl closes it again.

Notice what the theorem does not say. It does not say the result is a normal form; if the budget runs out mid-reduction, the half-reduced term is still a perfectly good witness of reachability. That limitation is part of the statement, and it is the statement that will follow the program out of Coq.

The recipe

Extraction is driven by a handful of directives that say what the target language is, how to render the datatypes Coq shares with it, and which functions to emit. The whole recipe fits on one screen:

Extraction Language Haskell.

Extract Inductive bool => "Prelude.Bool" ["Prelude.True" "Prelude.False"].
Extract Inductive option => "Prelude.Maybe" ["Prelude.Just" "Prelude.Nothing"].
Extract Inductive prod => "(,)" ["(,)"].
Extract Inductive list => "[]" ["[]" "(:)"].
Extract Inductive nat => "Prelude.Integer" ["0" "Prelude.succ"]
  "(\fO fS n -> if n Prelude.== 0 then fO () else fS (n Prelude.- 1))".

Extract Constant Nat.add => "(Prelude.+)".
Extract Constant Nat.pred => "(\n -> Prelude.max 0 (n Prelude.- 1))".
Extract Constant Nat.eqb => "(Prelude.==)".
Extract Constant Nat.leb => "(Prelude.<=)".
Extract Constant Nat.ltb => "(Prelude.<)".

Extraction "programs/lambda-eval/Eval.hs" eval step_fn cps psi.

The last line names four functions — the driver eval, the single step step_fn, and, from the call-by-value continuation-passing transform, cps and its value translation psi — and extraction pulls in everything they depend on.

The nat line is the representation change described at the top. Inside Coq a de Bruijn index is a unary numeral: 3 is S (S (S O)), three heap cells, and comparing two indices walks both. Extraction maps nat onto Haskell’s arbitrary-precision Integer, the two constructors onto 0 and Prelude.succ, and — the third argument — supplies a match function, so that a Coq match on S n becomes a test against zero and a subtraction. The Extract Constant lines then route the arithmetic to Haskell’s own operators instead of the extracted unary definitions. Every theorem above was proved about the inductive nat; the code that runs uses machine arithmetic.

The proofs themselves do not appear in the output at all. eval_sound and step_fn_sound live in Prop, the universe extraction erases wholesale, so there is no trace of them in the generated Haskell — they are statements about the Coq functions, and what carries them across is extraction’s own claim to preserve meaning. What does appear is the program, essentially unchanged. Here is the extracted step_fn, next to which you can hold the Coq definition from earlier:

step_fn :: Tm -> Prelude.Maybe Tm
step_fn t =
  case t of {
   App f a ->
    case is_value f of {
     Prelude.True ->
      case is_value a of {
       Prelude.True ->
        case f of {
         Abs b -> Prelude.Just (subst 0 a b);
         _ -> Prelude.Nothing};
       Prelude.False -> option_map (\x -> App f x) (step_fn a)};
     Prelude.False -> option_map (\f' -> App f' a) (step_fn f)};
   _ -> Prelude.Nothing}

Clause for clause the same function: the same three tests in the same order, option rendered as Maybe, and nothing inserted.

At the shell

Around the extracted core, Eval.hs, sits a hand-written command-line wrapper, Main.hs: a tokenizer and parser from named syntax like \x. x x to de Bruijn terms, a printer that invents fresh names on the way back, and a main that calls eval with a budget of a million steps. make lambda-eval compiles the two files together with GHC, and then:

$ ./programs/lambda-eval/lambda-eval '(\x. x x) (\y. y)'
\x. x
$ ./programs/lambda-eval/lambda-eval --cps '\x. x'
\x. \y. y x

The first is self-application: \x. x x duplicates the identity, applies it to itself, and settles at the identity, printed with a fresh name as \x. x.

The second is worth reading slowly, because --cps does not print the transformed program. It applies cps to the term, hands the result the identity continuation, and evaluates that. In continuation-passing style a function does not return; it calls a continuation with its result. What comes back is therefore not the value the direct evaluator would give, but that value’s converted twin, the one psi computes:

Ψ(λx.x)=λx.λk.kx\Psi(\lambda x.\,x) \;=\; \lambda x.\,\lambda k.\,k\,x

— a function that takes an argument and then a continuation, and hands the argument to the continuation. Printed with fresh names, that is \x. \y. y x, which is exactly the second line of output. The distinction between a value and its continuation-passing twin is a statement one proves in Coq; here it is a line you can read off a terminal.

What carries a proof and what does not

The evaluator is the verified part: step_fn is proved to agree with the step relation in both directions, and eval_sound says every answer is reachable from the input. Those facts describe the Haskell in Eval.hs to exactly the extent that extraction is faithful — which is assumed here, not proved.

Everything else is trusted. The parser and printer are about sixty lines of ordinary Haskell with no proof attached; a bug in either would show up as a term that was never the one you typed. GHC is trusted, as is the extraction machinery itself. And the step budget means a printed answer is guaranteed reachable but not guaranteed final: a term that needs more than a million steps prints whatever it had reached, and nothing in eval_sound distinguishes that from a finished reduction. Every one of these is a place where the chain from theorem to output can break, and naming them is the point — the unproved code is a thin, dull layer at the edge, and the interesting part sits behind it.
