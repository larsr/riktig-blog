The shape of the library

Write down “addition is associative” and you have written one sentence. But that sentence can be three completely different things, and which one it is decides who has to prove it and who gets to use it for free.

It can be a demand: I am about to reason about some structure, and I will only reason about structures where addition is associative. Nothing is proved; a requirement is announced.

It can be a consequence: given that demand, and a few others, here is something new that follows — cancellation, say, or that the identity element is unique. This is a real proof, but it is a proof about every structure meeting the demand at once, and it never mentions a particular set of numbers.

Or it can be a check: the integers, with Z.add, satisfy the demand — here is the stdlib lemma that says so. Nothing new is learned about associativity; a specific object is admitted to the club.

Mix the three and a library becomes unreadable in a specific way. You cannot tell, looking at a lemma, whether changing it obliges you to re-prove one thing or a hundred. You cannot tell whether a fact about integers was proved for integers — and so must be redone for rationals — or proved abstractly and merely used at the integers. The library described here keeps the three apart by one rule: a file does exactly one of these jobs, and the directory a file lives in says which.

The five layers

Below the three there are two more, and it is easier to read from the bottom up.

Ops.v is the vocabulary: one class per symbol, no laws at all.

Class EqRel T := equ : Rel T.
Infix "==" := equ (at level 70, no associativity).

Class Zero T := zero : T.
Notation "'0'" := zero.

Class HasAdd T := add : BinOp T.
Infix "+" := add.

That is the whole idea of the file: + means “there is an instance of HasAdd for this type”, and nothing else. Declaring HasAdd Z says integers have a binary operation written +; it says nothing about how it behaves.

Props.v holds single-law property classes — one named fact, about operations passed in as parameters:

Section LeftIdentityLaw.
  Context (A B : Type) {eqB : EqRel B} (action : A -> B -> B) (unit : A).
  Local Infix "·" := action (at level 40, left associativity).

  Class LeftIdentity := left_identity : forall x : B, unit · x == x.
End LeftIdentityLaw.

These exist so a proof can write rewrite left_identity no matter which structure supplied the law. Monoids, groups and rings all have identities; without Props.v each would export its own under a different name and every proof would have to know which structure it was standing in. The parameters reach further than they first look: what acts is an action, a function A -> B -> B, not necessarily an operation on one type — so LeftIdentity M M add 0 is a monoid’s 0 + x == x and LeftIdentity F V scale 1 is a vector space’s 1 *: u == u, one class serving both.

Interface/ states the demands. A structure class binds the operations as implicit parameters — not as fields — and holds the structure below it together with the laws it adds:

Module Monoid.
  Class Monoid (M : Type) {eq : EqRel M} {zero : Zero M} {add : HasAdd M} := {
    semigroup  :: Semigroup M add;
    is_left_identity  :: LeftIdentity M M add 0;
    is_right_identity :: RightIdentity M M add 0;
  }.
  Hint Mode Monoid ! - - - : typeclass_instances.
  Hint Rewrite @left_identity @right_identity : algebra_db.
End Monoid.
Export Monoid.

Three things in that block are worth reading slowly.

Every field uses :: rather than :. A field declared with :: is not merely a component you can project out — it is registered as a typeclass instance the moment a Monoid is in scope. So Monoid.semigroup makes associativity, and everything the semigroup holds beneath it, available wherever a monoid is; and the two identity fields make the identity laws findable, which is what lets rewrite left_identity fire without anything being named.

Those fields hold classes, not equations. LeftIdentity M M add 0 is the property class above, instantiated at this carrier, this action and this unit — the monoid does not restate 0 + x == x, it demands an instance of the law that says so. There is no seam between “the law this structure promises” and “the law spelled the way every proof wants to say it”: they are the same object, and the field is its registration.

And the whole thing sits inside Module Monoid, so the field semigroup is Monoid.semigroup and does not collide with Semigroup.magma or Group.monoid. The prefix lives in the module path rather than in the field name.

A richer structure holds its parent as its first field:

Module Group.
  Class Group (G : Type) {eq : EqRel G} {zero : Zero G} {add : HasAdd G}
              {neg : HasNeg G} := {
    monoid    :: Monoid G;
    neg_proper :: Proper (equ ==> equ) neg;
    is_left_inverse  :: LeftInverse G add neg 0;
    is_right_inverse :: RightInverse G add neg 0;
  }.
  Hint Mode Group ! - - - - : typeclass_instances.
  Hint Rewrite @left_inverse @right_inverse : algebra_db.
End Group.
Export Group.

Group.monoid is why “every group is a monoid” needs no instance anywhere: the group contains a monoid, and :: publishes it. From that one field, every monoid theorem applies to every group, with no further work at any use site — and the chain continues downward, since the monoid contains a semigroup and the semigroup a magma.

Theory/ holds the consequences: lemmas proved once, generically, over a Context. Impl/ holds the checks: concrete carriers with concrete operations and a proof that the laws hold for them. The next two sections are one of each.

A consequence: left cancellation

In a group, adding the same element on the left cannot lose information: if a+b=a+ca + b = a + c then b=cb = c. On the blackboard, the proof is a chain that adds −a-a on the left and re-associates:

b=0+b{left identity}=(−a+a)+b{left inverse}=−a+(a+b){associativity}=−a+(a+c){the hypothesis}=(−a+a)+c{associativity}=0+c{left inverse}=c{left identity}\begin{aligned} b &= 0 + b && \{\text{left identity}\}\\ &= (-a + a) + b && \{\text{left inverse}\}\\ &= -a + (a + b) && \{\text{associativity}\}\\ &= -a + (a + c) && \{\text{the hypothesis}\}\\ &= (-a + a) + c && \{\text{associativity}\}\\ &= 0 + c && \{\text{left inverse}\}\\ &= c && \{\text{left identity}\} \end{aligned}

The Coq proof, from Theory/Group.v, is that chain with the justifications in braces:

Theorem cancel_l : forall a b c : G, a + b == a + c -> b == c.
Proof.
  intros a b c Heq.
  calc b
    == (0 + b)          { left_identity  }
    == ((- a + a) + b)  { left_inverse }
    == (- a + (a + b))  { associative }
    == (- a + (a + c))  { Heq  }
    == ((- a + a) + c)  { associative }
    == (0 + c)          { left_inverse }
    == c                { left_identity  }.
Qed.

calc is a small notation that takes a starting term and a list of steps, each step giving the next term and the fact justifying it, and chains them by transitivity. Every justification here is a bare property-class method — left_identity, left_inverse, associative — resolved by instance search from whatever Group is in the Context. The proof never names a field of Group; it names the law, and the :: fields do the connecting.

Notice what the theorem does not mention: no integers, no rationals, no matrices. It is a theorem about the letter G.

A check: the integers

Impl/Zr.v says that Z is a ring, and it is short because every law is a stdlib lemma. First the symbols get their meanings:

#[global] Instance Z_EqRel : EqRel Z := eq.
#[global] Instance Z_Zero  : Zero Z := 0%Z.
#[global] Instance Z_One   : One Z := 1%Z.
#[global] Instance Z_Add   : HasAdd Z := Z.add.
#[global] Instance Z_Mult  : HasMult Z := Z.mul.
#[global] Instance Z_Neg   : HasNeg Z := Z.opp.

Then one instance per law, each pointing at the standard-library fact that proves it:

#[global] Instance Z_add_associative : Associative Z Z add add :=
  fun a b c => eq_sym (Z.add_assoc a b c).
#[global] Instance Z_add_left_identity : LeftIdentity Z Z add 0 := Z.add_0_l.
#[global] Instance Z_add_right_identity : RightIdentity Z Z add 0 := Z.add_0_r.
#[global] Instance Z_add_left_inverse : LeftInverse Z add neg 0 := Z.add_opp_diag_l.
#[global] Instance Z_add_right_inverse : RightInverse Z add neg 0 := Z.add_opp_diag_r.
#[global] Instance Z_add_commutative : Commutative Z add := Z.add_comm.

Z.add_assoc associates the other way round in the stdlib, so eq_sym flips it. And then the structures, which name no fields at all:

#[global] Instance Z_Magma : Magma Z add := { Magma.equivalence := eq_equivalence }.
#[global] Instance Z_Semigroup : Semigroup Z add := {}.
#[global] Instance Z_Monoid : Monoid Z := {}.
#[global] Instance Z_Group : Group Z := {}.
#[global] Instance Z_AbGroup : AbGroup Z := {}.

An empty {} asks instance search to fill every field, and the block above is what it finds. The Proper obligations are met the same way, by two instances declared next to the vocabulary and discharged with congruence, because == at Z is Leibniz equality and every function respects that. Multiplication then climbs the same ladder a second time — a magma, a semigroup and a monoid at Z.mul and 1 — and Ring Z falls out of the two of them with the distributive laws.

And then the generic theory applies, with nothing further to prove. The end of the same file:

Example z_mul_0_l : (0 * 7)%Z == 0.
Proof. exact (mul_0_l 7%Z). Qed.

mul_0_l is a theorem in Theory/Ring.v about an abstract ring. exact (mul_0_l 7%Z) applies it at Z — no Z-specific reasoning, no arithmetic, just the abstract theorem with the instance filled in by search. That is the entire return on the discipline: prove cancel_l once for Group, and integers, rationals, complex numbers, linear maps and matrices all have it, unconditionally, forever.

Three things the plain rule does not cover

The three-way split is a good rule precisely because it is sharp, and a sharp rule has edges. docs/DESIGN.md names three.

A Theory/ file may define an algorithm. Theory/BigOp.v defines bigop, the generic summation Fixpoint; Theory/GramSchmidt.v defines gram_schmidt. Neither is a derived theorem, so strictly neither belongs in Theory/. But there is no “Summation” or “Orthogonalization” interface for them to satisfy, and no concrete carrier they belong to — each is generic over an existing interface (Monoid, PosInner). The algorithm is the mathematics being studied, so it lives with the theory about it.

A Theory/ file may import a specific Impl/ file when its content is theory about that named representation. Theory/MatRep.v, Theory/Trace.v and Theory/Determinant.v all import Impl/Matrix.v, because their theorems cannot even be stated without naming matrices. The test is exactly that: could the file’s theorems be phrased without mentioning that representation? If not, the import is the point rather than a leak. The other direction stays forbidden — a generic construction over an abstract interface must not reach into a concrete representation.

Some tracks sit outside the split entirely. theories/Channel/, theories/Lambda/ and theories/Programs/ each study one concrete object — traces and protocols, a calculus, executable programs — rather than an abstract structure with many instances. There is exactly one alternating-bit protocol; giving it an Interface/ that some other Impl/ might satisfy differently would add layers without adding instances. So Channel/ABP.v keeps its data, its algorithm and its theorems in one file, in clearly separated sections, and states in its own header what it proves and what it deliberately does not. That is a different discipline applied consistently, not the absence of one.

The rule earns its keep exactly where many different things can satisfy one abstract contract, and has nothing to offer where the object of study is a single concrete thing.
