What is a mathematical structure?

Programmers already know half the answer. An interface says which operations exist: this thing can be compared, that thing can be concatenated. What an interface does not say is what the operations mean — a sort that returns its input untouched satisfies the type list -> list perfectly. A mathematical structure is the missing half: a vocabulary of operations together with the laws they obey.

That pairing is the whole idea, and everything in this series is built on it. This post says what it looks like written down, and then gives the two smallest structures.

A vocabulary, and laws over it

Many different things can be combined. Numbers add, strings concatenate, program fragments run one after another, rotations compose. Superficially these have nothing to do with each other, yet in every case the combining is associative:

(a⋅b)⋅c=a⋅(b⋅c).(a \cdot b) \cdot c = a \cdot (b \cdot c).

A structure is a name for a package such as “a set with one associative operation”. Anything satisfying the package is an instance of it, and — this is the part that pays — anything proved from the package alone holds for every instance at once, including instances nobody has thought of yet.

Two structures with the same operations but different laws are different worlds. Addition on the integers and multiplication on the integers offer the same vocabulary; only the first lets you undo, and that single difference is what the group post is about.

Laws, written once

If laws are what distinguish structures, they deserve to be written down once rather than restated inside each structure. Props.v is a catalogue that does exactly that: one entry per law, each stated over arbitrary operations.

Section ActionLaws.
  Context (A B : Type) {eqB : EqRel B} (action : A -> B -> B) (op : BinOp A).
  Local Infix "·" := action (at level 40, left associativity).
  Local Infix "⋆" := op (at level 40, left associativity).

  Class Associative := associative : forall (a b : A) (x : B), (a ⋆ b) · x == a · (b · x).
End ActionLaws.

Read the slots. Take B := A and action := op, and this is ordinary associativity of one operation on one set. Keep them distinct and it is the mixed law (ab)⋅x=a⋅(b⋅x)(a b) \cdot x = a \cdot (b \cdot x) that scaling a vector by scalars satisfies. One entry, both readings, and only ever one name to cite: associative.

The vocabulary is declared the same way, one class per symbol, in Ops.v:

Class Zero T := zero : T.
Class HasAdd T := add : BinOp T.

The == in the law above is not Coq’s built-in equality but each carrier’s own chosen equality. That, and the way Coq fills these in for you, is the subject of the Coq underneath.

The smallest structure

Start with as little as possible: a set with one binary operation and no laws at all. Mathematicians call it a magma. Here it is:

  Class Magma (M : Type) {eq : EqRel M} (op : BinOp M) := {
    equivalence :: Equivalence eq;
    op_proper   :: Proper (equ ==> equ ==> equ) op;
  }.

Neither field is a law about the operation. equivalence says the carrier’s chosen == really is an equivalence relation, and op_proper says the operation respects it — equal inputs give equal outputs. On the blackboard both are silent assumptions; in a library where each type picks its own equality they must be stated. So Magma is the mathematician’s magma plus the bookkeeping that makes a chosen equality behave like equality.

Add associativity and you have a semigroup:

(a+b)+c=a+(b+c)(a + b) + c = a + (b + c)

  Class Semigroup (S : Type) {eq : EqRel S} (op : BinOp S) := {
    magma       :: Magma S op;
    is_associative :: Associative S S op op;
  }.

Two fields: the weaker structure, held whole, and the one new law drawn from the catalogue. That shape repeats all the way up. A semigroup has a magma rather than restating its fields, so anything proved about magmas applies to semigroups with nothing copied — and the same again at every layer above.

What the layering buys

A theorem is proved at the weakest structure that supports it, and everything stronger inherits it. The identity element of a monoid is unique — proved in the next post from the identity laws alone — and that one proof serves the integers under addition, lists under concatenation, matrices under multiplication, and every monoid anyone adds later.

The instances are correspondingly small. Lists are a monoid, and Impl/ListMonoid.v says so by naming standard-library facts:

Instance app_associative A : Associative (list A) (list A) add add :=
  fun l m n => eq_sym (app_assoc l m n).
Instance app_left_identity A : LeftIdentity (list A) (list A) add 0 :=
  @app_nil_l A.
Instance app_right_identity A : RightIdentity (list A) (list A) add 0 :=
  @app_nil_r A.

after which the structure itself is a line with nothing in it, because every field is something search can already find:

Instance List_Monoid A : Monoid (list A) := {}.

The file ends with a remark as informative as the instances:

(* No AbGroup: app is not commutative and nothing here is invertible. *)

Lists stop at monoid. They cannot be a group, because appending something can never be undone by appending something else — which is exactly the property the group post starts from.
