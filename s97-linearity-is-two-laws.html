Linearity is two laws, and exp obeys one of them

A map ff between two vector spaces is called linear when it respects the two things a vector space can do to its vectors: add them, and scale them. That is two separate equations,

f(x+y)=f(x)+f(y)(additivity)f(x + y) = f(x) + f(y) \qquad\text{(additivity)}

f(a⋅x)=a⋅f(x)(homogeneity),f(a \cdot x) = a \cdot f(x) \qquad\text{(homogeneity)},

and they really are separate. Complex conjugation z↦z‾z \mapsto \bar z is additive, but not homogeneous over the complex scalars: az¯=a‾z‾\overline{a z} = \bar a \, \bar z, and a‾\bar a is not aa. In the other direction, the function f(x,y)=x3/(x2+y2)f(x,y) = x^3/(x^2+y^2) on the plane (with f(0,0)=0f(0,0)=0) satisfies f(ax,ay)=af(x,y)f(ax, ay) = a\,f(x,y) for every real aa, yet is not additive. Neither law implies the other, so a definition of “linear” has to state both.

Look at the additivity equation once more, without assuming the two sides live in the same world. On the left, xx and yy are combined by one operation before ff is applied; on the right, f(x)f(x) and f(y)f(y) are combined by another operation afterwards. Nothing in the shape of the law forces the two operations to be the same, or even to act on the same type. The exponential function satisfies

exp⁡(x+y)=exp⁡(x)⋅exp⁡(y):\exp(x + y) = \exp(x) \cdot \exp(y):

it carries addition to multiplication. It is “additive” in exactly the same sense a linear map is — same equation, different operation on the output side. Homogeneity has the same kind of slack: the scalar aa acts on the input one way (scaling a vector), acts on the output possibly another way (scaling a vector, or just multiplying a number, if ff lands in the scalars), and may even be transformed in transit, as conjugation transforms it in az¯=a‾z‾\overline{a z} = \bar a \, \bar z.

So “linear” decomposes into two independent laws, and each law is one equation-shape that recurs at many different operations. This post shows a formalization that takes both observations literally: one class per law, each parameterized by the operations it relates, and Linear assembled from the two by filling the slots in.

One law, any two operations

Throughout, == is each carrier’s chosen equivalence relation — the setoid equality this series always proves things up to — and a Class with one field declares a named, searchable fact: an Instance of it registers a proof that typeclass search can find whenever a later proof needs one. Here is additivity, from the law catalogue in Props.v:

Section HomomorphismLaws.
  Context (A B : Type) {eqB : EqRel B}.

  Section CarryingAnOperation.
    Context (opA : BinOp A) (opB : BinOp B) (f : A -> B).
    Local Infix "⋆" := opA (at level 40, left associativity).
    Local Infix "·" := opB (at level 40, left associativity).
    Class Additive := additive : forall x y : A, f (x ⋆ y) == f x · f y.
  End CarryingAnOperation.
End HomomorphismLaws.

Additive A B opA opB f says: f carries the operation opA on its source to the operation opB on its target. The two operations are ordinary parameters. Instantiate both with vector addition and this is the additivity of a linear map; instantiate the source side with add and the target side with mult and it is the exponential’s law. That second reading is not hypothetical — it is how the library’s Exp interface states the law of exponents, in Interface/Exp.v:

Class Exp (F : Type) `{OrderedField F} := {
  fn : F -> F;
  fn_proper :: Proper (equ ==> equ) fn;

  zero_to_one : fn 0 == 1;
  add_to_mul  :: Additive F F add mult fn;

  positive  : forall a : F, 0 <= fn a;

  monotone  : forall a b : F, a < b -> fn a < fn b;
}.

The field add_to_mul :: Additive F F add mult fn is exp⁡(x+y)=exp⁡(x)⋅exp⁡(y)\exp(x+y)=\exp(x)\cdot\exp(y), stated by the same class a linear map’s additivity uses, with different operations in the slots.

Scalars act, and the action is a parameter

Homogeneity needs one more piece of vocabulary. Scaling a vector is not a binary operation on one type: it takes a scalar from FF and a vector from VV and returns a vector — a function F→V→VF \to V \to V. A function of this shape, elements of one type modifying elements of another, is called an action of FF on VV. Laws about actions are stated with the action as a parameter, like this one at the top of Props.v:

Section ActionLaws.
  Context (A B : Type) {eqB : EqRel B} (action : A -> B -> B) (op : BinOp A).
  Local Infix "·" := action (at level 40, left associativity).
  Local Infix "⋆" := op (at level 40, left associativity).

  Class Associative := associative : forall (a b : A) (x : B), (a ⋆ b) · x == a · (b · x).
End ActionLaws.

Take B := A and action := op and this is ordinary associativity of one operation. Keep them distinct and it is the mixed-type law (ab)⋅x=a⋅(b⋅x)(a b) \cdot x = a \cdot (b \cdot x) that vector-space scaling satisfies. One class, both readings.

Homogeneity is stated the same way:

Section HomogeneityLaw.
  Context (F A B : Type) {eqB : EqRel B} {scaleA : HasScale F A}
          (action : F -> B -> B) (weight : F -> F) (f : A -> B).
  Local Infix "·" := action (at level 40, left associativity).

  Class Homogeneous := homogeneous : forall (a : F) (x : A), f (a *: x) == weight a · f x.
End HomogeneityLaw.

Read it slot by slot. On the source side, a *: x is the scaling that A already carries (*: is the notation for whatever HasScale F A provides). On the target side, the scalar acts through the action parameter — which need not be a scaling. If f lands back in the scalars themselves, the natural way for a to act on the output is plain field multiplication, and action := mult says so. And before acting, the scalar passes through weight : F -> F: the identity for an ordinary linear map, but the slot is exactly where conjugation would go for a map like z↦z‾z \mapsto \bar z, whose scalars come out conjugated. The law-shape f(a*:x)=w(a)⋅f(x)f(a \mathbin{*:} x) = w(a) \cdot f(x) covers all of these with one definition.

Assembling Linear

With both laws in the catalogue, the definition of a linear map is just a matter of filling in slots, in Interface/Linear.v:

Class Linear (F U V : Type)
    {eU : EqRel U} {aU : HasAdd U} {sU : HasScale F U}
    {eV : EqRel V} {aV : HasAdd V} {sV : HasScale F V}
    (f : U -> V) := {
  proper         :: Proper (equ ==> equ) f;
  is_additive    :: Additive U V add add f;
  is_homogeneous :: Homogeneous F U V scale (fun a => a) f;
}.

Three fields. proper says f sends ==-equal inputs to ==-equal outputs — the license every rewrite under f needs, since == is a chosen equivalence rather than Coq’s built-in equality. is_additive is the Additive class at add on both sides. is_homogeneous is the Homogeneous class with the target-side action filled by V’s own scaling and the weight filled by the identity function. Nothing here is new; Linear names a particular way of filling in two reusable laws.

The :: on each field re-exports it as an instance in its own right: any Linear proof in scope makes the underlying Additive and Homogeneous facts individually visible to typeclass search. That matters because of what comes next.

What stating the laws separately buys

A theorem whose proof uses only additivity should be stated for every additive map, not re-proved once for linear maps, once for group homomorphisms, once for bilinear maps with one argument frozen. The model case: an additive map between groups sends zero to zero. The blackboard proof adds f(0)f(0) to both sides and cancels,

f(0)+f(0)=f(0+0)=f(0)=f(0)+0,f(0) + f(0) = f(0+0) = f(0) = f(0) + 0,

so cancelling f(0)f(0) on the left leaves f(0)=0f(0) = 0. In Theory/Group.v, with f any map between two groups carrying the constraint fa : Additive G K add add f:

  Theorem additive_zero : f 0 == 0.
  Proof.
    apply (cancel_l (f 0)).
    calc (f 0 + f 0)
      == (f (0 + 0)) { (additive 0 0) }
      == (f 0)       { left_identity }
      == (f 0 + 0)   { right_identity }.
  Qed.

cancel_l (f 0) is the group cancellation law from early in this series, turning the goal f 0 == 0 into f 0 + f 0 == f 0 + 0; the calc chain is then the displayed equation read left to right, one law per step: additive — the class field, so the additivity comes from whatever instance is in scope — folds the sum inside f, left_identity collapses 0 + 0, and right_identity re-expands f 0 to f 0 + 0 to meet the goal’s right-hand side.

Taking the hypothesis as a class constraint rather than an ordinary argument costs nothing and buys the common case. Additive has a single field which is the equation, so a caller with no registered instance still hands the proof over directly, as additive_zero f (fa := my_proof). There is therefore just one theorem, not one convenient version and one general version.

Linear maps are the case where nothing needs handing over at all. Interface/LinearMap.v packages a function with its Linear proof, whose is_additive field is an Additive instance, so the zero law is one line naming only the map:

  Theorem linear_map_zero : f 0 == 0.
  Proof.
    exact (additive_zero (lm_fun f)).
  Qed.

Had additivity been fused into a monolithic “linearity” axiom, this reuse would need glue at every step. Stated as its own class, the group-level theorem applies directly.

One caveat marks the boundary of the abstraction. exp is Additive F F add mult fn, so one might hope exp⁡(0)=1\exp(0)=1 falls out of additive_zero the same way. It does not: additive_zero needs both sides to be groups, and (F,⋅)(F, \cdot) is not one — 00 has no multiplicative inverse. That is why zero_to_one : fn 0 == 1 appears as a separate axiom in the Exp class above rather than as a consequence.

A linear map you can compute: a matrix times a vector

The concrete instance everyone meets first: fix a matrix AA and send the vector vv to AvAv, with entries (Av)i=∑jAijvj(Av)_i = \sum_j A_{ij} v_j. In Theory/MatVec.v, over any field, with bigopF the sum over a finite index type:

Definition mat_vec {m n : nat} (A : Matrix m n F) (v : Fin.t n -> F)
    : Fin.t m -> F :=
  fun i => bigopF (fun j => A i j * v j).

Additivity is distributivity pushed through the sum, entry by entry:

(A(v+w))i=∑jAij(vj+wj)=∑j(Aijvj+Aijwj)=∑jAijvj+∑jAijwj.\big(A(v+w)\big)_i = \sum_j A_{ij}(v_j + w_j) = \sum_j \big(A_{ij} v_j + A_{ij} w_j\big) = \sum_j A_{ij} v_j + \sum_j A_{ij} w_j.

Lemma mat_vec_add : forall (m n : nat) (A : Matrix m n F)
    (v w : Fin.t n -> F),
  mat_vec A (v + w) == mat_vec A v + mat_vec A w.
Proof.
  intros m n A v w i.
  calc (mat_vec A (v + w) i)
    == (bigopF (fun j => A i j * v j + A i j * w j))
    == ((mat_vec A v + mat_vec A w) i).
  - apply bigopF_ext. intros j.
    exact (left_distributive (A i j) (v j) (w j)).
  - exact (bigopF_add n (fun j => A i j * v j) (fun j => A i j * w j)).
Qed.

intros ... i fixes the entry at which the two vectors are compared (vector equality here is entrywise). The first calc step rewrites each summand by left_distributive — the field’s distributivity, via bigopF_ext, which may rewrite under a sum precisely because the sum respects ==. The second step is bigopF_add, splitting the sum of pointwise sums into two sums: the last equality of the displayed chain.

Homogeneity is the mirror image, with commutativity of multiplication doing the reordering Aij(avj)=a(Aijvj)A_{ij}(a v_j) = a (A_{ij} v_j) inside the sum and bigopF_mul_l pulling the constant aa out:

Lemma mat_vec_scale : forall (m n : nat) (A : Matrix m n F) (a : F)
    (v : Fin.t n -> F),
  mat_vec A (a *: v) == a *: mat_vec A v.
Proof.
  intros m n A a v i.
  calc (mat_vec A (a *: v) i)
    == (bigopF (fun j => a * (A i j * v j)))
    == ((a *: mat_vec A v) i).
  - apply bigopF_ext. intros j.
    exact (mul_left_commutative (A i j) a (v j)).
  - exact (bigopF_mul_l n a (fun j => A i j * v j)).
Qed.

The two laws plus a Proper proof assemble into the packaged linear map, through the record’s builder function:

Definition mat_vec_lm {m n : nat} (A : Matrix m n F) :
    LinearMap F (Fin.t n -> F) (Fin.t m -> F) :=
  linear_map_from_laws
    (mat_vec A)
    (mat_vec_proper_v m n A)
    (mat_vec_add m n A)
    (mat_vec_scale m n A).

From this point on, mat_vec A is not a function that happens to satisfy two equations — it is a LinearMap, and everything proved about linear maps in general (linear_map_zero above, composition, the vector-space structure on the maps themselves) applies to it with no further argument.

One step up: linear in each slot

A function of two vector arguments, like matrix multiplication (A,B)↦AB(A, B) \mapsto AB, is usually not linear as a map on pairs — doubling both factors quadruples the product. The right notion is bilinear: freeze either argument and the remaining one-argument function is linear. The definition in Interface/Bilinear.v says exactly that, by using Linear twice:

Class Bilinear (F U V W : Type)
    {Fe : EqRel F} {Fz : Zero F} {Fa : HasAdd F} {Fn : HasNeg F} {Fo : One F}
    {Fm : HasMult F} {Fi : HasInv F} {FF : Field F}
    {eU : EqRel U} {zU : Zero U} {aU : HasAdd U} {nU : HasNeg U} {sU : HasScale F U}
    {VU : VectorSpace F U}
    {eV : EqRel V} {zV : Zero V} {aV : HasAdd V} {nV : HasNeg V} {sV : HasScale F V}
    {VV : VectorSpace F V}
    {eW : EqRel W} {zW : Zero W} {aW : HasAdd W} {nW : HasNeg W} {sW : HasScale F W}
    {VW : VectorSpace F W}
    (b : U -> V -> W) := {
  proper :: Proper (equ ==> equ ==> equ) b;

  linear_l :: forall v : V, Linear F U W (fun u => b u v);
  linear_r :: forall u : U, Linear F V W (b u);
}.

The long implicit prefix is the field and the three vector spaces with their operations; the content is the last two fields, one Linear instance per slot. Note what the slot laws jointly imply: expanding both arguments gives b(u+u′,v+v′)=b(u,v)+b(u,v′)+b(u′,v)+b(u′,v′)b(u+u', v+v') = b(u,v) + b(u,v') + b(u',v) + b(u',v') — four terms, not the two that additivity-on-pairs would give. Bilinear and “linear on the product space” are genuinely different properties.

Matrix multiplication is the working example, registered in Theory/MatMulBilinear.v from its four slot laws (additive and homogeneous in the left factor, additive and homogeneous in the right):

Definition mat_mul_bilinear :
    BilinearMap F (Matrix m n F) (Matrix n p F) (Matrix m p F) :=
  bilinear_map_from_laws
    (mat_mul (F:=F) (m:=m) (n:=n) (p:=p))
    (mat_mul_proper m n p)
    (mat_mul_add_l m n p)
    (mat_mul_scale_l m n p)
    (mat_mul_add_r m n p)
    (mat_mul_scale_r m n p).

And the pattern keeps scaling. A multilinear form takes nn vector arguments, returns a scalar, and is linear in each argument with the others frozen. The Multilinear class in Interface/Bilinear.v states the per-slot laws with the same two classes this post started from — upd vs i x is the family vs of nn vectors with its ii-th member replaced by x, so each frozen-slot function is literally fun x => form (upd vs i x):

is_additive :: forall (vs : Fin.t n -> V) (i : Fin.t n),
  Additive V F add add (fun x => form (upd vs i x));
is_homogeneous :: forall (vs : Fin.t n -> V) (i : Fin.t n),
  Homogeneous F V F mult (fun a => a) (fun x => form (upd vs i x));

Look at the Homogeneous slot: the action parameter is mult, because the form lands in the scalars, where a scalar acts by plain multiplication — the exact flexibility the parameter was built for. The determinant is the special case where the form is additionally alternating; but that is its own story. The point here is smaller and sharper: additivity and homogeneity, each stated once as a class with its operations as parameters, are enough vocabulary to define linear maps, the exponential’s law, bilinear maps, and nn-linear forms — without restating a single equation.
