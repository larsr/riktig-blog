The maps between vector spaces form a vector space

Having defined vector spaces, the next question is which functions between them are worth studying. The answer — the ones that respect the two things a vector space can do — leads somewhere pleasant: those functions are themselves a vector space, and when the source and target coincide they are also a ring. Two structures from earlier posts appear where you might not have expected them.

Two laws, kept apart

A map f:U→Vf : U \to V is linear when

f(x+y)=f(x)+f(y)andf(a*:x)=a*:f(x).f(x + y) = f(x) + f(y) \qquad\text{and}\qquad f(a *: x) = a *: f(x).

The two are independent — complex conjugation satisfies the first and not the second — so both are demanded, and each is a separate entry in the law catalogue rather than a clause of one big definition:

  Class Linear (F U V : Type)
      {eU : EqRel U} {aU : HasAdd U} {sU : HasScale F U}
      {eV : EqRel V} {aV : HasAdd V} {sV : HasScale F V}
      (f : U -> V) := {
    proper         :: Proper (equ ==> equ) f;
    is_additive    :: Additive U V add add f;
    is_homogeneous :: Homogeneous F U V scale (fun a => a) f;
  }.

Keeping them apart is what lets a theorem ask for exactly what it uses. additive_zero from the group post needs additivity and nothing else, so it applies to a linear map without any glue:

  Theorem linear_map_zero : f 0 == 0.
  Proof.
    exact (additive_zero (LinearMap.map f)).
  Qed.

A linear map sends 00 to 00 — not by a fresh calculation, but because the :: on is_additive makes every Linear proof supply an Additive one, and the group theorem asks for that. linear_map_neg is the same line for negation. There is a whole post on why the two laws are stated over arbitrary operations; here it is enough that they are separate.

A map and its proof travel together as one object:

Module LinearMap.
  Class LinearMap (F U V : Type)
      {eU : EqRel U} {aU : HasAdd U} {sU : HasScale F U}
      {eV : EqRel V} {aV : HasAdd V} {sV : HasScale F V} := {
    map    : U -> V;
    linear :: Linear F U V map;
  }.
End LinearMap.

with Coercion LinearMap.map : LinearMap >-> Funclass, so a LinearMap can be applied to a vector like any function.

When are two maps equal?

Before the maps can form a vector space they need an equality, and there is only one sensible choice: two maps are equal when they agree everywhere.

  #[export] Instance linear_map_equ : EqRel (LinearMap F U V) :=
    fun f g => forall u : U, f u == g u.

This is a good illustration of why the library carries a chosen equality per carrier. Two LinearMap records could hold different proof terms and still be the same map; Coq’s built-in equality would distinguish them, and the mathematics does not. Pointwise agreement does, and it is an equivalence relation, which is what the next paragraph needs.

The maps are a vector space

Write Hom(U,V)\mathrm{Hom}(U,V) for the linear maps from UU to VV. Define

(f+g)(u)=f(u)+g(u),(a*:f)(u)=a*:f(u),0(u)=0,(f + g)(u) = f(u) + g(u), \qquad (a *: f)(u) = a *: f(u), \qquad 0(u) = 0,

and each of these is linear again — which has to be checked, and is, one small lemma per law. Then all the vector-space laws hold, each because it holds pointwise in the target. So Hom(U,V)\mathrm{Hom}(U,V) is a vector space, and Theory/HomVS.v finishes with:

  #[export] Instance Hom_VectorSpace : VectorSpace F Hom := {}.

Empty braces again: every field has already been supplied. What is worth noticing is the shape of the argument. Each law for the map space — associativity of ++, the identity laws, the inverse laws, commutativity — is proved by applying the same law in VV at each argument. The theorems are named hom_associative, hom_left_identity, hom_left_inverse and so on, matching the law each one supplies.

When source and target agree

Take U=VU = V and something extra appears: two linear maps from VV to itself can be composed, and composition is another operation on the same carrier. Write End(V)\mathrm{End}(V) for these, the endomorphisms. Composition is associative, the identity map is a unit for it, and it distributes over pointwise addition. Those are exactly the ring axioms:

  #[export] Instance End_One : One EndV := linear_map_id.

  #[export] Instance End_Mult : HasMult EndV :=
    fun f g : EndV => linear_map_comp f g.

And associativity of the multiplication is free — composing functions is associative by how application works, so the proof does not even need a chain:

  Lemma end_mul_associative : forall f g h : EndV, (f * g) * h == f * (g * h).
  Proof.
    intros f g h u.
    reflexivity.
  Qed.

intros … u uses the chosen equality: to prove two maps equal it is enough to prove them equal at an arbitrary u, and there both sides are literally the same term.

This ring is the first in the series that is not commutative — doing ff then gg generally differs from doing gg then ff. The ring post was careful never to assume otherwise, and this is what that care was for. Matrices, later, are a way of writing these maps down in coordinates; the ring they form is this one.
