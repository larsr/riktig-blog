Structures grow arrows: category theory up to CCC

A mathematical structure — a group, a ring, a vector space — is an interface with laws, and it is usually studied from the inside: a group is a set with +, 0, - obeying laws. Category theory makes one radical move: it forgets the inside. You are not allowed to ask what an object contains — only how it connects. Everything must be said with arrows.

The surprise, and the one idea of this post: products, function types, and lambda calculus can be reconstructed from arrows alone, and anything reconstructed this way transports to every world that has the right arrows. It is the “prove once, hold everywhere” trick one level up — not laws about elements, but laws about composition itself. (Our tour follows the classic route of Bartosz Milewski’s Category Theory for Programmers, which is the recommended companion reading.)

A category: the algebra of composition

A category has objects and arrows (morphisms) between them. Arrows compose associatively, and every object has a do-nothing arrow. That’s all. In theories/Structure/Category.v:

Module Category.
  Class Category (obj : Type) := {
    hom : obj -> obj -> Type;
    id   : forall {x : obj}, hom x x;
    comp : forall {x y z : obj}, hom y z -> hom x y -> hom x z;
    is_left_identity  :: forall x y, LeftIdentity (hom y y) (hom x y) comp id;
    is_right_identity :: forall x y, RightIdentity (hom x x) (hom x y) comp id;
    comp_associative    : forall (w x y z : obj) (f : hom y z) (g : hom x y) (h : hom w x),
        comp f (comp g h) == comp (comp f g) h
    (* ... hom-equality is a setoid, composition respects it ... *)
  }.
End Category.
Export Category.
Notation cat_id   := Category.id.

Notation "x ~> y" := (Category.hom x y) (at level 70, right associativity).
Infix "∘" := Category.comp (at level 40, left associativity).

Squint and you’ll recognize the monoid laws from the post on mathematical structures — associativity and two identities — except ∘ is only defined when the arrows fit end-to-end. A category is a typed monoid; a monoid is a category with one object. The two posts are studying the same phenomenon at different resolutions.

The two identity fields make that literal. LeftIdentity and RightIdentity are the same standalone law classes a monoid uses — LeftIdentity A B action unit says unit · x == x for a unit in A acting on a B. A monoid instantiates them at one carrier; a category instantiates them at comp viewed as an action of the endomorphisms hom y y on the arrows hom x y. Nothing is restated, only aimed somewhere new. The readable form of each law is a two-line definition just below the class:

  Definition comp_left_identity {obj : Type} `{Category obj}
    (x y : obj) (f : hom x y) : comp id f == f := left_identity f.

One Coq detail is load-bearing: equality of arrows (==) is a setoid per hom — chosen equality, not built-in equality. That choice is why, later in this post’s companion, programs modulo equivalence can be the arrows of a category. Wire equality in too tightly and syntax categories become impossible.

Two categories we now own, machine-checked:

  • Coq’s own types and functions (Impl/CoqCat.v): objects are types, arrows are functions, == is pointwise equality. This is Milewski’s Set, the category programmers secretly live in.
  • Lambda terms modulo conversion (Impl/StlcCat.v): objects are simple types, an arrow A ~> B is a program of type A → B, and two arrows are equal when a conversion relation says the programs behave alike. The file’s conv is deliberately a small fragment of full βη-conversion — three generators (conv_beta_id, conv_beta_comp, conv_eta) plus congruence and weakening, exactly the instances the category laws need; the file discloses the scope cut in its header. Composition is λx. g (f x), and the category laws are conversion facts. More on this in the post on lambda terms you can run.

“The” needs a theorem: initial and terminal objects

With arrows only, how do you point at a specific object? By a property of its arrows. A terminal object has exactly one arrow coming in from everywhere; an initial object exactly one going out to everywhere. The whole interface (Structure/Category.v) is three fields:

Module Terminal.
  Class Terminal {O : Type} (C : Category O) := {
    term                : O;
    morphism            : forall x : O, x ~> term;
    morphism_uniqueness : forall (x : O) (f : x ~> term), f == morphism x
  }.
End Terminal.
Export Terminal.
Notation terminal_morphism := Terminal.morphism.

In Coq-types: unit is terminal (every type has exactly one function into it), the empty type is initial (Structure/Category.v is the mirror image, with init and emit).

But saying “the terminal object” is an obligation: what if there are two? The first real theorem of the category track (Theory/InitialTerminal.v) discharges it: any two terminal objects are isomorphic. It deserves the same slow walk that cancel_l got in the post on mathematical structures, because it is the first proof in the project conducted entirely with arrows — no elements anywhere.

First, what is claimed. An isomorphism between objects x and y is a pair of arrows that undo each other (Theory/Category.v):

Module TwoSidedInverse.
  Class TwoSidedInverse {O : Type} `{Category O} {x y : O}
      (f : x ~> y) (g : y ~> x) := {
    from_to : g ∘ f == cat_id;
    to_from : f ∘ g == cat_id;
  }.
End TwoSidedInverse.

Class Iso (x y : O) := {
  iso_to : x ~> y;
  iso_from : y ~> x;
  iso_inverse :: TwoSidedInverse iso_to iso_from;
}.

The two round-trip laws are stated once, about a pair of morphisms, in the class TwoSidedInverse; Iso then carries the two morphisms as data and one field holding the proof that they are each other’s inverse. Splitting it that way lets a pair of morphisms written at a use site be shown mutually inverse without being packaged into an Iso first, and lets instance search recognise morphisms it already has. The two laws are still available under the names a caller would expect — iso_fromto and iso_tofrom are projections out of iso_inverse — and iso_from_laws builds an Iso from the two morphisms and the two laws, in that order.

Next, the only lemma the proof needs: every endomorphism of a terminal object is the identity. Why? Both f and cat_id are arrows into a terminal object, and Terminal.morphism_uniqueness says there is only one of those:

Lemma term_endo_id (T : Terminal C) :
  forall f : term (Terminal:=T) ~> term (Terminal:=T), f == cat_id.
Proof.
  intros f.
  rewrite (morphism_uniqueness _ f).
  symmetry.
  apply morphism_uniqueness.
Qed.

Read it: f == terminal_morphism term (uniqueness, applied to f), and cat_id == terminal_morphism term (uniqueness, applied to cat_id), hence f == cat_id. The proof never opens an object; it plays two uses of the same law against each other.

Finally the theorem. Given two terminal objects T1, T2, where do the two arrows of the isomorphism come from? There is no choice to make: T2’s terminal morphism at T1 is an arrow T1 ~> T2, and vice versa. Their composites are endomorphisms of terminal objects — identities, by the lemma. The construction hands iso_from_laws the only inhabitants the types allow:

Definition terminal_iso (T1 T2 : Terminal C) :
  Iso (term (Terminal:=T1)) (term (Terminal:=T2)) :=
  iso_from_laws
    (terminal_morphism (Terminal:=T2) (term (Terminal:=T1)))
    (terminal_morphism (Terminal:=T1) (term (Terminal:=T2)))
    (term_endo_id T1 _)
    (term_endo_id T2 _).

(initial_iso is the same proof with all arrows reversed. And since any arrow into a terminal object is the terminal morphism, the isomorphism could not have been anything else — that uniqueness is immediate from Terminal.morphism_uniqueness, though the file does not state it as a separate theorem.) Uniqueness-up-to-iso is category theory’s notion of “the”, and from here on the project earns every definite article it uses.

Products, exponentials, CCC: the rest of the reconstruction

The remaining structures play the same game the terminal object just played — pick out an object by a universal property of its arrows — so we state them at a glance and let the files speak.

A product of a and b (Structure/Category.v) is an object with projections pi1, pi2 through which any object mapping into both a and b factors, uniquely (HasProducts.pi1_pair, HasProducts.pi2_pair, HasProducts.uniqueness). No mention of “pairs of elements” — yet in Coq-types this is exactly prod/fst/snd, and Theory/Product.v derives the working algebra (pair_eta, pair_comp, commutativity of × up to iso). An exponential (Structure/Category.v) internalizes the arrows a ~> b as an object exp_obj a b, with an application arrow eval_morphism and a currying operation whose central law is

curry_beta       : forall (x a b : O) (h : prod_obj x a ~> b),
    eval_morphism ∘ (curry h ×× cat_id) == h;

— currying then applying is the original function; Theory/Exponential.v proves the inverse round trip (curry_uncurry, uncurry_curry) in the usual few rewrite lines.

A category with a terminal object, all products, and all exponentials is cartesian closed (Structure/Category.v) — three capabilities bundled:

𝐂𝐂𝐂=nothing+pairing+function types\textbf{CCC} \;=\; \text{nothing} \;+\; \text{pairing} \;+\; \text{function types}

And the tower’s capstone instance, at the bottom of Impl/CoqCat.v:

Instance CoqCCC : CCC CoqCat :=
  @CCC.Build_CCC Type CoqCat
    CoqTerminal
    CoqProducts
    CoqExponentials.

Coq’s own types form a cartesian closed category, machine-checked, no axioms added. Why this is the right stopping point for today: CCCs are exactly the worlds where lambda calculus makes sense. The curry/eval algebra is the typing of λ and application; Impl/StlcCat.v is the syntactic side of that same coin. Which is the cliffhanger for the post on lambda terms you can run: lambda terms as a formal, executable object — with variables done right.
