What is a mathematical structure?

Programmers already know half of what a mathematical structure is. An interface says which operations exist: this thing can be compared, that thing can be concatenated. What an interface does not say is what the operations mean. A sort function that returns its input untouched satisfies the interface list -> list perfectly; nothing in the type list -> list says the output must be ordered. The meaning lives outside the interface.

A mathematical structure is the missing half: the vocabulary of operations together with the laws those operations must obey. Not “there is a +”, but “there is a +, and it never matters how you parenthesise a sum”. The laws are the meaning. Two structures with the same operations but different laws are different worlds — and anything you prove from the laws alone holds in every world that satisfies them, at once. This post builds the smallest such structure, the monoid, and then proves one small theorem about every monoid there will ever be.

The monoid: combine, with a do-nothing element

Many different things can be combined. Numbers add. Strings and lists concatenate. Program fragments run one after another. In each case the combining operation shares two properties. First, it is associative: regrouping a chain of combinations changes nothing,

(a+b)+c=a+(b+c).(a + b) + c \;=\; a + (b + c).

Second, there is a do-nothing element — zero for addition, the empty string for concatenation, the empty program for sequencing — that combines invisibly, on the left and on the right:

0+a=a,a+0=a.0 + a \;=\; a, \qquad a + 0 \;=\; a.

A set with a combining operation +, a do-nothing element 0, and those laws is a monoid. The integers under addition are a monoid. Lists under concatenation are a monoid (a different one: concatenation is not commutative, [1] + [2] is not [2] + [1], but it is still associative with the empty list as its 0). Naming the shared pattern is what lets a single proof serve all of them.

Vocabulary and laws, kept in separate files

The encoding in this library keeps the vocabulary and the laws apart on purpose, so each can be reused. The vocabulary is one tiny typeclass per symbol, stating that an operation exists and saying nothing about how it behaves. Here are the two the monoid needs, from Ops.v:

Class Zero T := zero : T.
Notation "'0'" := zero.

Class HasAdd T := add : BinOp T.
Infix "+" := add.

That is the entire content of Zero and HasAdd: a designated element and a binary operation, with the familiar notation attached. Once a type provides HasAdd, the literal symbol + works for it.

A law is also a first-class, nameable thing — one class per law, in Props.v. Here are the three the monoid needs:

Section ActionLaws.
  Context (A B : Type) {eqB : EqRel B} (action : A -> B -> B) (op : BinOp A).
  Local Infix "·" := action (at level 40, left associativity).
  Local Infix "⋆" := op (at level 40, left associativity).

  Class Associative := associative : forall (a b : A) (x : B), (a ⋆ b) · x == a · (b · x).
End ActionLaws.

Section LeftIdentityLaw.
  Context (A B : Type) {eqB : EqRel B} (action : A -> B -> B) (unit : A).
  Local Infix "·" := action (at level 40, left associativity).

  Class LeftIdentity := left_identity : forall x : B, unit · x == x.
End LeftIdentityLaw.

Section RightIdentityLaw.
  Context (A B : Type) {eqB : EqRel B} (action : B -> A -> B) (unit : A).
  Local Infix "·" := action (at level 40, left associativity).

  Class RightIdentity := right_identity : forall x : B, x · unit == x.
End RightIdentityLaw.

Each is stated for an action — a function A -> B -> B letting an element of one type act on an element of another — and Associative takes in addition an operation ⋆ combining two elements of A. A monoid uses all three at A = B = M with the action being + itself: Associative M M add add then reads (a + b) + x == a + (b + x), LeftIdentity M M add 0 reads 0 + x == x, and RightIdentity M M add 0 reads x + 0 == x — the three blackboard laws. The extra generality is not idle: a scalar acting on a vector obeys the same three laws with A the scalars and B the vectors, so they never have to be written twice. Because these are named classes, a proof can write rewrite associative no matter which structure supplied the associativity — the law is found by matching the goal, not by naming its source. (== is the carrier’s own equality, the class EqRel, so the machinery works for structures whose equality is not Coq’s built-in =; only B, the type the law’s equation is about, needs one.)

The structure itself is a class stating those laws over that vocabulary, and it is assembled in three files, each holding the one below it as a field. The bottom is a carrier with an operation and an equality the operation respects, from Interface/Magma.v:

Module Magma.
  Class Magma (M : Type) {eq : EqRel M} (op : BinOp M) := {
    equivalence :: Equivalence eq;
    op_proper   :: Proper (equ ==> equ ==> equ) op;
  }.
  Hint Mode Magma ! - - : typeclass_instances.
End Magma.
Export Magma.

Magma.equivalence says == really is an equivalence relation (reflexive, symmetric, transitive), and Magma.op_proper says the operation respects it — replacing either argument by an equal one gives an equal result, which is what Proper (equ ==> equ ==> equ) op spells out. Both are declared with :: rather than :, which makes the field itself an instance, so rewrite may use it under a + without the magma being mentioned. The Hint Mode line keeps instance search from hunting for a magma before it knows the carrier. The Module wrapper is a namespace: inside it the fields carry plain names, and from outside they are read qualified — Magma.equivalence, Magma.op_proper — while the closing Export puts the class in scope under its short name.

Associativity turns a magma into a semigroup, and the two identity laws turn that into a monoid — Interface/Semigroup.v and Interface/Monoid.v in their entirety:

Module Semigroup.
  Class Semigroup (S : Type) {eq : EqRel S} (op : BinOp S) := {
    magma       :: Magma S op;
    is_associative :: Associative S S op op;
  }.
  Hint Mode Semigroup ! - - : typeclass_instances.
  Hint Rewrite @associative : algebra_db.
End Semigroup.
Export Semigroup.
Module Monoid.
  Class Monoid (M : Type) {eq : EqRel M} {zero : Zero M} {add : HasAdd M} := {
    semigroup         :: Semigroup M add;
    is_left_identity  :: LeftIdentity M M add 0;
    is_right_identity :: RightIdentity M M add 0;
  }.
  Hint Mode Monoid ! - - - : typeclass_instances.
  Hint Rewrite @left_identity @right_identity : algebra_db.
End Monoid.
Export Monoid.

Read the monoid’s header first: the class takes the vocabulary as parameters — an EqRel, a Zero and a HasAdd for the carrier M — so Monoid M presupposes the operations and contributes only laws. Its three fields are one substructure and two laws. Monoid.semigroup is the semigroup itself, held as a field: because it is declared with ::, a proof standing in an arbitrary monoid can use anything a semigroup or a magma provides, found by projection with nothing said. And Monoid.is_left_identity does not restate 0 + x == x; it is a LeftIdentity, the law class above, at this carrier, this action and this unit. That is what lets a later proof write rewrite left_identity and have Coq find the monoid’s own law by matching the + and the 0 in the goal — the field is the registration, there is no separate step. The two Hint Rewrite lines additionally file the laws in a database, so autorewrite with algebra_db can apply them without any of them being named.

The payoff: the identity element is unique

Now a theorem that holds in every monoid, proved once. Suppose you have two candidate do-nothing elements: an e that is a left identity (e + a == a for all a) and an f that is a right identity (a + f == a for all a). They must be equal. The argument is a single trick — look at the combination e + f from both sides:

e=e+f{f is a right identity}=f{e is a left identity}e \;=\; e + f \quad\{\text{$f$ is a right identity}\}\quad =\; f \quad\{\text{$e$ is a left identity}\}

The first equality holds because f does nothing on the right; the second because e does nothing on the left. Here is the proof exactly as it appears in Theory/Monoid.v:

Theorem id_unique : forall e f : M,
  (forall a, e + a == a) -> (forall a, a + f == a) -> e == f.
Proof.
  intros e f He Hf.
  calc e
    == (e + f) { (Hf e) }
    == f       { (He f) }.
Qed.

The calc block is the blackboard chain, machine-checked. It reads e == (e + f) == f, and each { ... } names the one fact that justifies that step; the checker confirms the written endpoints really are the goal (e == f) and fills each step by that fact. Walking it:

  • intros e f He Hf names the two elements and their identity hypotheses — He : forall a, e + a == a and Hf : forall a, a + f == a.
  • == (e + f) { (Hf e) } is the step e = e + f. The justification Hf e is the fact e + f == e; the checker uses it right-to-left.
  • == f { (He f) } is the step e + f = f, justified by He f, which is exactly e + f == f.

Two identities, sandwiched around one product, forced to coincide.

The theorem the rest of the library actually calls has one identity named up front — the structure’s own 0 — and a candidate compared against it. That is a one-step corollary. A left identity must be the zero:

e=e+0{right identity law}=0{hypothesis e+a=a at a=0}e \;=\; e + 0 \quad\{\text{right identity law}\}\quad =\; 0 \quad\{\text{hypothesis } e + a = a \text{ at } a = 0\}

Theorem zero_unique_l : forall e : M, (forall a, e + a == a) -> e == 0.
Proof.
  intros e He.
  calc e
    == (e + 0) { right_identity    }
    == (0 : M) { (He 0) }.
Qed.

The first step, e = e + 0, is the monoid’s own right-identity law right_identity (used right-to-left). The second, e + 0 = 0, is the hypothesis He at the argument 0. Its mirror image is zero_unique_r, with the statement forall e : M, (forall a, a + e == a) -> e == 0 — a right identity is the zero too, proved the same way through e = 0 + e = 0.

A monoid you can compute with

None of this is abstract for its own sake: the moment a concrete type is shown to satisfy the Monoid class, all of the above becomes true of it with no further work. Lists under concatenation are the first instance. The vocabulary comes first — an equality, a zero, an addition, registered for list A in Impl/ListMonoid.v:

#[global] Instance List_EqRel A : EqRel (list A) := eq.
#[global] Instance List_Zero  A : Zero (list A) := nil.
#[global] Instance List_Add   A : HasAdd (list A) := @app A.

Then the laws, one instance per law, each discharged by the corresponding fact from Coq’s standard library:

#[global] Instance app_associative A : Associative (list A) (list A) add add :=
  fun l m n => eq_sym (app_assoc l m n).
#[global] Instance app_left_identity A : LeftIdentity (list A) (list A) add 0 :=
  @app_nil_l A.
#[global] Instance app_right_identity A : RightIdentity (list A) (list A) add 0 :=
  @app_nil_r A.

The identity laws are app_nil_l (prepending the empty list changes nothing) and app_nil_r (appending it changes nothing). The one wrinkle is app_associative: the standard library states associativity as l ++ (m ++ n) = (l ++ m) ++ n, the mirror image of the class’s, so eq_sym flips it around.

With the laws in the instance database, the three structures are declared with almost nothing in them:

#[global] Instance List_Magma A : Magma (list A) add :=
  { Magma.equivalence := eq_equivalence }.
#[global] Instance List_Semigroup A : Semigroup (list A) add := {}.
#[global] Instance List_Monoid A : Monoid (list A) := {}.

An empty {} asks instance search to supply every field: the semigroup’s magma field resolves to List_Magma and its is_associative field to app_associative, and the monoid’s semigroup, is_left_identity and is_right_identity fields resolve to List_Semigroup and the two identity instances. The one field written out is Magma.equivalence, filled with the standard library’s eq_equivalence, its proof that Coq’s = is an equivalence relation.

The integers under addition follow the same recipe: Impl/Zr.v registers Z’s vocabulary (Z_EqRel, Z_Zero, Z_Add) and the same three laws — Z_add_associative, Z_add_left_identity, Z_add_right_identity, discharged by Z.add_assoc, Z.add_0_l and Z.add_0_r — before declaring Z_Monoid, as part of the richer structure the next post introduces. Both carriers inherit id_unique and zero_unique_l for free: whatever left identity you can find in Z under +, or in list A under concatenation, is provably the one already named 0.
