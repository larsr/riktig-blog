Getting started: five imports, five domains

Reading a proof someone else wrote is not the same as writing one. This post is five short working examples, one per major area of a Coq mathematics library, each in the same shape: state something abstractly, against an interface, then prove a concrete instance satisfies it. The five are checked in as theories/Examples/GettingStarted.v and rebuilt with the tree, so if a library change breaks anything shown here, the build breaks there.

Why the imports are the hard part

The first thing that stops a newcomer is not the mathematics. It is figuring out which files to Require.

Nothing collides, which is what makes generous imports safe in the first place. Each structure class sits inside a module of its own name that is then Exported, so Field.Field is also reachable as plain Field, and a structure’s derived facts stay qualified when the short name would be ambiguous — Category.comp_left_identity rather than a bare comp_left_identity. The individual algebraic laws are not duplicated per structure at all: there is exactly one Associative, one LeftIdentity, one RightInverse, and so on, defined once in Props.v, and each structure declares an instance of them. A monoid’s own definition reads

  Class Monoid (M : Type) {eq : EqRel M} {zero : Zero M} {add : HasAdd M} := {
    semigroup         :: Semigroup M add;
    is_left_identity  :: LeftIdentity M M add 0;
    is_right_identity :: RightIdentity M M add 0;
  }.

so left_identity is a single global name whose meaning is fixed by which operation and which unit typeclass search picks for it. Files that mint instances prefix their names — PW_ in Theory/Pointwise.v, LV_ in Impl/ListVS.v, C_ in Impl/Complex.v, Hom_ in Theory/HomVS.v. Importing more than you need cannot shadow anything.

What files do not do is re-export uniformly. Require Export passes a file’s own imports on to whoever asks for it; Require Import keeps them private. The algebra tower exports: Theory/AbGroup.v begins From Riktig Require Export Interface.AbGroup Theory.Group, and because each of those exports its own parents in turn, asking for it hands you the ==/+/- notation and the law names associative, commutative, right_inverse along with the theorems. The category files import: Theory/Category.v begins From Riktig Require Import Ops Interface.Category Lib.Calc, so a client that asks only for Theory/Category.v gets the theorems but no ==, and the first == in a statement fails with Syntax Error: Lexer: Undefined token — correct, but not obviously pointing at the fix.

There is no way to tell which kind a file is without opening it. So: a cheat sheet, checked by actually writing the code.

The preamble, all of it, before anything else

The checked-in file opens with every import the five examples need, and no Section before them:

From Coq Require Import ZArith Morphisms QArith Bool List.
From Coq.Vectors Require Fin.
Import ListNotations.
From Riktig Require Import Theory.AbGroup Impl.Zr Interface.LinearMap
  Impl.Qf Impl.FinVec Theory.Category Impl.CoqCat Lambda.Church
  Channel.Trace.

Eight names, not the seventeen an earlier version of this file listed. Theory.AbGroup carries Interface.AbGroup, Theory.Group, Ops and Props with it; Interface.LinearMap carries Interface.Field and Interface.VectorSpace; Impl.CoqCat carries Theory.Category; Lambda.Church carries Lambda.Syntax and Lambda.Conv; Channel.Trace carries Theory.Subseq. Naming an ancestor as well as its descendant compiles perfectly and says nothing — the shorter list is the one that tells you what the file is written against.

One Riktig line per domain, in the order the examples come. That layout is not cosmetic; the pitfall in example 2 below is what forced it.

1. Algebra

Abstract statement, over any abelian group:

Section Generic.
  Context {G : Type} `{AbGroup G}.

  Theorem swap_cancel : forall a b c : G, (a + b) + (c + - a) == b + c.
  Proof.
    intros a b c.
    rewrite (commutative a b), (associative (op := add)), (add_swap_l a c (- a)), right_inverse, right_identity.
    reflexivity.
  Qed.
End Generic.

Concrete instance, over ℤ:

Example z_swap_cancel : (3 + 5 + (7 + - 3))%Z = (5 + 7)%Z.
Proof. exact (swap_cancel (G := Z) 3%Z 5%Z 7%Z). Qed.

What the imports do. Nothing in the type of swap_cancel mentions Props, but commutative, associative, right_inverse and right_identity are the names of the single-law property classes that live there — the ones the AbGroup class binds its own axioms to. Interface.AbGroup supplies the class the Context line asks for, Theory.AbGroup supplies add_swap_l, and Impl.Zr supplies the ℤ instance the concrete example resolves against. The first two are strictly redundant — Theory.AbGroup exports them, so Theory.AbGroup alone compiles the same proof. Naming them anyway documents what the proof depends on, which is worth one line.

The one annotation to notice is (op := add). The other four laws are applied to arguments (commutative a b), and the arguments pin down which operation is meant. associative is applied to nothing here, so nothing pins it down: Associative in Props.v is stated for an action A -> B -> B together with an operation on A, and without op := add the elaborator has two unknowns and no way to choose. Supplying the operation by name is shorter than supplying three explicit arguments, and it is the usual way the tree resolves this in a rewrite.

2. Linear algebra

Abstract statement, over any linear map:

Section Generic.
  Context {F U V : Type} `{FF : Field F}.
  Context {eU : EqRel U} {zU : Zero U} {aU : HasAdd U} {nU : HasNeg U} {sU : HasScale F U}.
  Context {VU : VectorSpace F U}.
  Context {eV : EqRel V} {zV : Zero V} {aV : HasAdd V} {nV : HasNeg V} {sV : HasScale F V}.
  Context {VV : VectorSpace F V}.

  Theorem lm_combination : forall (f : LinearMap F U V) (a b : F) (u v : U),
    f (a *: u + b *: v) == a *: f u + b *: f v.
  Proof.
    intros f a b u v.
    rewrite (linear_map_additive f), (linear_map_scale f), (linear_map_scale f).
    reflexivity.
  Qed.
End Generic.

Concrete instance: a scaling map on ℚ2\mathbb{Q}^2 (Fin.t 2 -> Q), built from the field’s own scale laws. A LinearMap is a record holding a function together with a proof that the function is linear, and linear_map_from_laws builds one from the function and its three laws — respects ==, respects +, respects scaling:

Section ScaleMap.
  Context {F V : Type} `{FF : Field F}.
  Context {eV : EqRel V} {zV : Zero V} {aV : HasAdd V} {nV : HasNeg V} {sV : HasScale F V}.
  Context {VV : VectorSpace F V} (c : F).

  #[export] Instance scale_map_proper : Proper (equ ==> equ) (fun v : V => c *: v).
  Proof.
    intros u v Huv.
    rewrite Huv.
    reflexivity.
  Qed.

  Lemma scale_map_add : forall u v : V, c *: (u + v) == c *: u + c *: v.
  Proof.
    intros u v.
    exact (left_distributive c u v).
  Qed.

  Lemma scale_map_scale : forall (a : F) (u : V),
    c *: (a *: u) == a *: (c *: u).
  Proof.
    intros a u.
    rewrite <- (associative c a u), (mul_comm c a),
      (associative a c u).
    reflexivity.
  Qed.

  Definition scale_map : LinearMap F V V :=
    linear_map_from_laws
      (fun v : V => c *: v)
      scale_map_proper
      scale_map_add
      scale_map_scale.
End ScaleMap.

Definition triple : LinearMap Q (Fin.t 2 -> Q) (Fin.t 2 -> Q) :=
  scale_map (3#1)%Q.

Example fin2_combo : forall u v : Fin.t 2 -> Q,
  triple (2 *: u + 5 *: v) == 2 *: triple u + 5 *: triple v.
Proof. intros u v. exact (lm_combination triple (2#1)%Q (5#1)%Q u v). Qed.

The non-obvious pitfall: import order, not import contents. Writing Impl.Qf/Impl.FinVec after the generic Section (rather than at the top of the file) made scalar multiplication resolve to the field’s self-scaling instance before the vector type was pinned down — a flexible-carrier typeclass search picking the wrong instance silently, producing a baffling type mismatch on a line that looked completely correct. Moving every import above every Section fixed it outright. Rule of thumb: all imports first, always — this codebase’s Hint Mode discipline (documented in project memory as the fix for a much worse historical bug — a compiler-crashing search divergence) depends on the carrier being syntactically pinned down before instance search fires, and import order can undermine that even when every individual import is correct.

3. Category theory

Abstract statement, over any category, about isomorphisms:

Section Generic.
  Context {O : Type} `{Category O}.

  Theorem iso_absorb : forall (x y : O) (f : Iso x y),
    (iso_from f ∘ iso_to f) ∘ iso_from f == iso_from f.
  Proof.
    intros x y f.
    rewrite (iso_fromto f), Category.comp_left_identity.
    reflexivity.
  Qed.
End Generic.

Category.comp_left_identity is one of the places where the qualified name earns its keep. A category’s identity law is an instance of the same LeftIdentity class the monoid used, at comp and id; the category file wraps that instance in a named definition of its own,

  Definition comp_left_identity {obj : Type} `{Category obj}
    (x y : obj) (f : hom x y) : comp id f == f := left_identity f.

so that a rewrite in a categorical proof can name the law it wants without leaving typeclass search to guess between the hom-set’s composition and whatever other operation happens to be in scope.

Concrete instance: bool is isomorphic to itself via negb (types-as-objects, Impl/CoqCat.v). An Iso holds the two morphisms plus one field saying they are two-sided inverses of each other, and iso_from_laws builds it from the two morphisms and the two round-trip proofs — here both negb_involutive, since negb is its own inverse:

Definition negb_negb_iso : @Iso Type CoqCat bool bool :=
  iso_from_laws negb negb negb_involutive negb_involutive.

Example negb_absorb : forall b : bool, negb (negb (negb b)) = negb b.
Proof. exact (iso_absorb _ _ negb_negb_iso). Qed.

The sharpest trap of this whole post is why Theory/Category.v writes Global Arguments iso_to {x y}. and not the plain Arguments iso_to {x y}. that would look sufficient. Iso is declared inside a Section, and a non-Global Arguments directive is section-local: it silently reverts the moment the section closes, so anyone who just Require Imports the file gets back the fully-explicit signature with no warning given. The symptom is not a clean “wrong number of arguments” — it is a type mismatch buried in typeclass elaboration, because Coq inserts fresh implicits for the class’s own parameters and then feeds your argument into the wrong slot. Print Implicit iso_from is what shows you the mismatch. The general lesson: if you write Arguments {x y}. inside a Section and mean it to survive export, say Global Arguments.

4. Lambda calculus

Abstract fact (the earlier lambda-calculus post’s if_of_true-style branch law), instantiated at two concrete closed terms:

Example ifb_true_idt_k : IFB TRUE idt k == idt.
Proof.
  apply IF_TRUE.
  - apply value_abs.
  - apply value_abs.
Qed.

(* Cross-check: the same fact, by running the evaluator on both sides
   and comparing normal forms. *)
Example ifb_true_idt_k_by_eval : IFB TRUE idt k == idt.
Proof. apply (conv_by_eval 20 5). reflexivity. Qed.

Two independent proofs of the same statement — one by the algebraic law, one by brute-force evaluation — agreeing, is itself a small sanity check on the whole conv setoid built in that earlier lambda-calculus post. No import surprises here: Lambda/Church.v carries its own comment naming exactly what it needs from Ops.

5. Channels

A concrete fact about a specific loss pattern, then the same fact via a general lattice lemma:

Local Open Scope nat_scope.

Example drop_middle : lossy [1; 2; 3] [1; 3].
Proof. apply subseq_keep, subseq_drop, subseq_keep, subseq_nil. Qed.

Example perfect_is_lossy_123 : lossy [1; 2; 3] [1; 2; 3].
Proof. apply perfect_lossy. reflexivity. Qed.

The non-obvious import, in the other direction from example 2: Channel/Trace.v is generous with Require Export — it exports both List and Theory/Subseq.v, which is why subseq_keep and friends are in scope here without being asked for. But it also does a plain Import ListNotations. at its own top, and Import, unlike Export, does not propagate to a client file. Leave that line out of your own file and the very first [1; 2; 3] fails with Syntax error: '.' expected — the library file you are building on visibly did the import, and it still does not reach you. That is why the preamble above repeats Import ListNotations. for itself.

The Local Open Scope nat_scope. shown with the examples is the other half of the same story, and it is a consequence of gathering all five domains into one file. QArith (example 2) puts Q_scope on top of the numeral stack, and Lambda.Conv (example 4) re-points the lonely 1 at nat’s S O; without re-opening nat_scope just before them, the list literals [1; 2; 3] elaborate at mixed types. Reopening a scope is cheap; hunting the elaboration error that follows from not doing it is not.

The cheat sheet

I want to… Import
use ==, +, *:, - notations at all Ops
name a law like commutative/associative/right_inverse directly Props
state something over an abstract Monoid/Group/AbGroup/Ring/Field Interface.<Name>
use derived facts (cancel_l, mul_0_l, …) Theory.<Name>
work with vectors/linear maps abstractly Interface.VectorSpace, Interface.LinearMap
a concrete field to compute in Impl.Qf (ℚ), Impl.Zr (ℤ), Impl.Complex (ℂ)
a concrete finite-dimensional space Impl.FinVec (Fin n -> F with its dot product)
categories, functors, isomorphisms Interface.Category, Theory.Category
Coq’s own types as a category Impl.CoqCat
the lambda calculus, runnable Lambda.Syntax (eval), Lambda.Conv (the == setoid), Lambda.Church (booleans/pairs)
channel fault models Channel.Trace

Two rules generalize past this list. Put every import before every Section — import order can silently redirect instance search, and the fix is never obvious from the error. And do not rely on a file re-exporting what it uses: the algebra tower does, the category files do not, Import never does. Naming what you depend on costs one line and removes the question.
