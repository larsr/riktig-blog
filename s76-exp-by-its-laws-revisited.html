Exp, by its laws

The exponential function is usually introduced by a construction: a power series, or a limit of (1+a/n)n(1 + a/n)^n. Both need real-analysis machinery — convergence, completeness — before anything can be said about exp at all. There is a second way in, and this post takes it: write down the laws exp must obey, prove the consequences from those laws alone, and leave the construction for later. Four laws turn out to be enough for a surprising amount, and they also mark precisely where the algebra stops and analysis has to begin.

Laws instead of a formula

Stated as a class over an ordered field:

Module Exp.
  Class Exp (F : Type) `{OrderedField F} := {
    fn : F -> F;
    fn_proper :: Proper (equ ==> equ) fn;

    zero_to_one : fn 0 == 1;
    add_to_mul  :: Additive F F add mult fn;

    positive  : forall a : F, 0 <= fn a;

    monotone  : forall a b : F, a < b -> fn a < fn b;
  }.
  Hint Mode Exp ! - - - - - - - - - - - : typeclass_instances.
End Exp.
Export Exp.
Notation exp_fn := Exp.fn.

Four laws — Exp.fn_proper is setoid plumbing, not a law about exp itself: it says exp_fn respects the equality == (whose relation is named equ), and the :: in its declaration registers that fact as an instance, so rewrite can replace equals under exp_fn with nothing further declared. The module is the prefix: the laws are Exp.zero_to_one, Exp.add_to_mul, Exp.positive and Exp.monotone, and the function keeps the short global spelling exp_fn.

Exp.add_to_mul is named rather than spelled out. Additive A B opA opB f is a small reusable class saying f (x ⋆ y) == f x · f y for a chosen pair of operations, so Additive F F add mult fn is the equation fn (a + b) == fn a * fn b, written in the vocabulary that also states what a linear map does to sums. exp is a monotone homomorphism from the additive group (F,+,0)(F,+,0) to the multiplicative monoid (F,×,1)(F,\times,1), landing in the nonnegative numbers. Nothing here says how to compute it — a power-series or limit-based construction is separate, later work, the same relationship Structure/Reals.v has to a construction of the reals. Anything satisfying these four laws is legally “an exp” for every theorem downstream, whether it’s ever been evaluated.

What four laws buy for free

Small, cheap corollaries, all proved generically — no construction, no concrete F, just algebra:

Lemma exp_neg : forall a : F, exp_fn (- a) == inv (exp_fn a).
Lemma exp_nonzero : forall a : F, exp_fn a =/= 0.
Lemma exp_strict_pos : forall a : F, 0 < exp_fn a.
Lemma exp_injective : forall a b : F, exp_fn a == exp_fn b -> a == b.

The nonvanishing fact is the nicest of these, because it comes free from a law that looks unrelated: exp a * exp (-a) == exp 0 == 1 exhibits exp a as invertible directly, so if it were 0 the field would be forced to satisfy 0 == 1 — impossible in any field worth the name. No case split, no separate axiom; the homomorphism law alone makes exp a a unit.

exp_injective is the more interesting one to sit with, because it’s half of the fact that makes log possible at all: exp : F -> F is a bijection onto the positive elements. Injectivity — different inputs give different outputs — falls out of strict monotonicity with no extra assumptions. Surjectivity — every positive element is some exp a — is the harder half, and it needs completeness (the least- upper-bound property Structure/Reals.v states but doesn’t yet build a witness for). So log is not derivable from these four laws, and Theory/Log.v does not pretend otherwise: it assumes surjectivity outright, as the section hypothesis forall y : F, 0 < y -> {x : F | exp_fn x == y}, and defines log_fn from the witness that hypothesis hands it — a construction of exp over a complete field is what would discharge it. This file gets you exactly as far as the algebra allows and stops there rather than assuming ahead.

The one thing deliberately left out

Every calculus class’s favorite fact about exp — that it’s its own derivative — is not in this file, and the reason is worth stating plainly rather than glossing over. All four laws are algebraic and order-theoretic; not one of them mentions a limit, so no statement about a derivative follows from them, for any candidate derivative. The vocabulary for writing “exp′ = exp” down does exist: exp_fn is checked against Theory/Derivative.v’s is_deriv, which asks the codomain to carry a NormedSpace structure and packages the derivative as a LinearMap, and Theory/MLDerivatives.v supplies both for a bare field — Field_NormedSpace norms F over itself by abs, and lm_scale_map is the map h ↦ c * h. What no file in the tree supplies is the analytic fact itself, which would have to come from a construction of exp.

So it is not added to Exp as a fifth field. Doing that would make every user of Exp — including code that only ever evaluates the function, never differentiates it — carry a NormedSpace-over-itself structure just to make the class typecheck. Instead the one file that needs exp’s derivative takes it as a section hypothesis, one line, right where it is used:

  Context (exp_is_deriv : forall a : F, is_deriv exp_fn a (lm_scale_map (exp_fn a))).

Everything proved in that section — the chain rule through exp_fn (c * x), for instance — then carries the hypothesis in its own statement, so a reader can see exactly which unproved fact it rests on, and a later construction of exp over a complete field would discharge it once for all of them.
