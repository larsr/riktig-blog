A matrix is an operator

A matrix is usually met twice, in two different roles that a first course rarely separates. It is a rectangle of numbers you can add, scale and multiply by the row-times-column rule; and it is a thing that acts — feed it a column of numbers and it gives back another column. The second role is the one that explains the first. Matrix multiplication looks arbitrary as a formula on rectangles; as an operation on actions it is nothing but do one, then the other.

Two questions come out of that. First: is the action of a matrix really a linear map — a function that respects addition and scaling — or is that just a slogan? Second: if it is, does the row-times-column formula genuinely compute composition of those maps, or only something that resembles it? Both have checkable answers, and the second one has a practical consequence: whenever you would form a matrix product only to apply it to a vector, you never have to form the product at all.

What a matrix does

A matrix of mm rows and nn columns over a field FF is a function from a row index and a column index to a scalar; there is nothing to it beyond that:

Definition Matrix (m n : nat) (F : Type) : Type :=
  Fin.t m -> Fin.t n -> F.

Fin.t n is the type of indices 0,…,n−10,\dots,n-1, so a coordinate vector of length nn is a function Fin.t n -> F. Such functions form a vector space with no extra work — add and scale them pointwise.

Applying a matrix to a coordinate vector is the textbook dot product of each row against the vector, written as a finite sum bigopF over the shared index (Theory/MatVec.v):

  Definition mat_vec {m n : nat} (A : Matrix m n F) (v : Fin.t n -> F)
      : Fin.t m -> F :=
    fun i => bigopF (fun j => A i j * v j).

Entry ii of A⋅vA\cdot v is ∑jAijvj\sum_j A_{ij}\,v_j.

The action is linear, and that is a theorem

Linearity is a property of a plain function: it respects the equivalence == each type carries, it turns sums into sums, and it pulls scalars out. Theory/MatVec.v proves the two algebraic halves for mat_vec A. Additivity is distributivity pushed under the sum:

∑jAij(vj+wj)=∑j(Aijvj+Aijwj){distributivity}=∑jAijvj+∑jAijwj{sums split}.\sum_j A_{ij}(v_j + w_j) \;=\; \sum_j \bigl(A_{ij}v_j + A_{ij}w_j\bigr) \quad\{\text{distributivity}\}\;=\; \sum_j A_{ij}v_j + \sum_j A_{ij}w_j \quad\{\text{sums split}\}.

  Lemma mat_vec_add : forall (m n : nat) (A : Matrix m n F)
      (v w : Fin.t n -> F),
    mat_vec A (v + w) == mat_vec A v + mat_vec A w.
  Proof.
    intros m n A v w i.
    calc (mat_vec A (v + w) i)
      == (bigopF (fun j => A i j * v j + A i j * w j))
      == ((mat_vec A v + mat_vec A w) i).
    - apply bigopF_ext. intros j.
      exact (left_distributive (A i j) (v j) (w j)).
    - exact (bigopF_add n (fun j => A i j * v j) (fun j => A i j * w j)).
  Qed.

Walking it: intros ... i fixes an output index, since two coordinate vectors are equal when they agree at every index. The calc chain has two steps, one per line of the blackboard chain — bigopF_ext rewrites the summand by distributivity, and bigopF_add splits the sum of two summands into a sum of two sums.

Homogeneity is the same shape with a commutativity swap instead of distributivity:

  Lemma mat_vec_scale : forall (m n : nat) (A : Matrix m n F) (a : F)
      (v : Fin.t n -> F),
    mat_vec A (a *: v) == a *: mat_vec A v.

Linear F U V f is the class collecting exactly these three facts about a function f — Linear.proper, Linear.is_additive, Linear.is_homogeneous — and a LinearMap F U V (Interface/LinearMap.v) is a function together with a proof that it is linear, two fields and no more. Its implicit binders are only what the two laws literally mention — an equality, an addition and a scaling on each carrier:

Record LinearMap (F U V : Type)
    {eU : EqRel U} {aU : HasAdd U} {sU : HasScale F U}
    {eV : EqRel V} {aV : HasAdd V} {sV : HasScale F V} := {
  lm_fun :> U -> V;
  lm_linear :: Linear F U V lm_fun;
}.

Nothing here demands that F be a field or that U and V be vector spaces. Additivity and homogeneity can be stated with only + and *: in hand, so those are the only assumptions the record makes; the field and vector-space structure appear later, in the theorems that need them — linear_map_zero needs a zero to preserve, and negation to cancel with.

The :> on lm_fun is what lets a caller write f u rather than lm_fun f u, and the :: on lm_linear registers the linearity proof where instance search can find it. So the three lemmas package a matrix as a value of that record, built by linear_map_from_laws from the function and its three laws:

  Definition mat_vec_lm {m n : nat} (A : Matrix m n F) :
      LinearMap F (Fin.t n -> F) (Fin.t m -> F) :=
    linear_map_from_laws
      (mat_vec A)
      (mat_vec_proper_v m n A)
      (mat_vec_add m n A)
      (mat_vec_scale m n A).

A matrix denotes a linear map between coordinate spaces — as a value that every theorem about linear maps accepts.

Multiplication is composition

Now the second question. On the blackboard, entry (i,k)(i,k) of A⋅BA\cdot B is ∑jAijBjk\sum_j A_{ij}B_{jk}, and applying that to vv gives

((AB)v)i=∑k(∑jAijBjk)vk=∑jAij(∑kBjkvk){exchange the two sums}=(A(Bv))i.\bigl((A B)\,v\bigr)_i \;=\; \sum_k \Bigl(\sum_j A_{ij}B_{jk}\Bigr) v_k \;=\; \sum_j A_{ij}\Bigl(\sum_k B_{jk}v_k\Bigr) \quad\{\text{exchange the two sums}\} \;=\; \bigl(A\,(B\,v)\bigr)_i .

The only real content is the exchange of the two finite sums — the same exchange that proves matrix multiplication associative. So the theorem can be had from associativity rather than redoing the exchange:

  Theorem mat_vec_mul : forall (m n p : nat) (A : Matrix m n F)
      (B : Matrix n p F) (v : Fin.t p -> F),
    mat_vec (mat_mul A B) v == mat_vec A (mat_vec B v).
  Proof.
    intros m n p A B v i.
    exact (mat_mul_assoc m n p 1 A B
             (fun (k : Fin.t p) (_ : Fin.t 1) => v k) i Fin.F1).
  Qed.

Walking it: intros ... i again reduces to one output index. The term fun (k : Fin.t p) (_ : Fin.t 1) => v k views v as a matrix with pp rows and a single column. Under that view mat_vec (mat_mul A B) v i and mat_vec A (mat_vec B v) i are, by unfolding alone, the entry (i,col 0)(i, \text{col }0) of the two bracketings of the triple product ABvA\,B\,v — so mat_mul_assoc, applied at the shapes m n p 1 and read at row i and the sole column Fin.F1, is already the proof. The same one-column view gives the identity law from mat_mul_left_identity:

  Theorem mat_vec_id : forall (n : nat) (v : Fin.t n -> F),
    mat_vec mat_id v == v.

And at the level of the packaged maps, mat_vec_lm sends the matrix product to composition of linear maps:

  Theorem mat_vec_lm_mul : forall (m n p : nat) (A : Matrix m n F)
      (B : Matrix n p F),
    mat_vec_lm (mat_mul A B) == linear_map_comp (mat_vec_lm A) (mat_vec_lm B).
  Proof.
    intros m n p A B v.
    exact (mat_vec_mul m n p A B v).
  Qed.

Equality of linear maps here is agreement at every argument, so intros ... v turns the goal into mat_vec_mul at v — the two statements are the same fact, once at the level of functions and once at the level of the record.

Using it: never form the product

Read mat_vec_mul from right to left and it stops being an identity and becomes a choice of algorithm. To compute (A⋅B)⋅v(A\cdot B)\cdot v you may instead compute A⋅(B⋅v)A\cdot(B\cdot v): two matrix-vector applications, no matrix product, no m×pm \times p intermediate ever stored.

Counting the scalar multiplications the definitions perform: forming A⋅BA\cdot B costs mnpm\,n\,p (there are mpm p entries, each a sum of nn products) and applying it to vv costs a further mpm\,p, for mnp+mpm n p + m p in total. The other order costs npn p to form B⋅vB\cdot v and mnm n to apply AA to the result — np+mnn p + m n. With mm, nn, pp all around a thousand that is a billion multiplications against two million.

The saving is not an approximation to be checked afterwards. The two expressions are provably the same coordinate vector, so a program may pick either one and a caller cannot tell the difference.

What is not settled here is which linear maps arise this way at all. mat_vec_lm goes from matrices to maps between the concrete coordinate spaces Fin.t n -> F; the converse direction — every linear map between finite-dimensional spaces has a matrix, once bases are chosen — is a separate result over abstract spaces, in Theory/MatRep.v, where no coordinates are given in advance and a basis has to supply them.
