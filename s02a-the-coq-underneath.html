The Coq underneath: chosen equality, classes, and chains

Every post in this series shows mathematics and then the Coq that transcribes it. The transcription uses the same half-dozen devices every time, and rather than re-explain them in each post, this one explains them once. Four questions, in order: what does == mean, how does a proof find the law it needs, why does rewriting need permission, and what is a calc chain.

Nothing here is specific to any one structure. If you have read the monoid post you have already seen all of it in use.

Equality is chosen, not given

Coq has a built-in equality, written =, and it means these two terms are the same term. That is often too strong. A rational number written 1/21/2 and one written 2/42/4 are not the same pair of integers, yet every theorem about the rationals treats them as the same number. The same happens for functions equal at every argument, matrices equal entry by entry, sets with the same members.

The standard remedy is to carry the relation with the type. A set with a chosen equivalence relation — reflexive, symmetric, transitive — is called a setoid, and the relation plays the part equality plays on the blackboard. In this library the relation is equ, written ==, and it is supplied per type by Ops.v:

Class EqRel T := equ : Rel T.
Infix "==" := equ (at level 70, no associativity).

For the rationals, Impl/Qf.v chooses Qeq, the standard library’s “equal as fractions”:

Instance Q_EqRel : EqRel Q := Qeq.

so 1/2 == 2/4 holds while 1/2 = 2/4 does not. For the integers, Impl/Zr.v chooses ordinary equality — Instance Z_EqRel : EqRel Z := eq — because there nothing needs identifying. Both are groups, and every theorem proved about groups applies to each with its own notion of sameness.

One class per symbol, one class per law

A type class is a family of facts indexed by a type, and an Instance registers a member of that family. When a proof needs a member, Coq searches the registered instances and fills it in, the way a compiler resolves an overloaded operator. That search is the mechanism doing the work everywhere below.

Ops.v declares one class per symbol — nothing about behaviour:

Class Zero T := zero : T.
Class HasAdd T := add : BinOp T.
Class HasNeg T := neg : T -> T.
Class HasScale F V := scale : F -> V -> V.

Props.v declares one class per law, each stated over arbitrary operations rather than over + or * in particular:

Section InverseLaws.
  Context (T : Type) {eqT : EqRel T} (op : BinOp T) (inverse : T -> T) (unit : T).
  Local Infix "⋆" := op (at level 40, left associativity).

  Class LeftInverse  := left_inverse  : forall a, inverse a ⋆ a == unit.
  Class RightInverse := right_inverse : forall a, a ⋆ inverse a == unit.
End InverseLaws.

Two things follow from stating the law this way. The same class serves wherever the shape recurs — LeftInverse is about something undoing something, not about negation — and the law acquires a stable name, left_inverse, which is what proofs cite. A proof step justified by left_inverse does not say which structure’s inverse law it means; search resolves that from the goal.

A structure such as Monoid is then a class whose fields are laws, and whose symbols arrive as parameters in braces:

  Class Monoid (M : Type) {eq : EqRel M} {zero : Zero M} {add : HasAdd M} := {
    semigroup         :: Semigroup M add;
    is_left_identity  :: LeftIdentity M M add 0;
    is_right_identity :: RightIdentity M M add 0;
  }.

The symbols are parameters and not fields for a concrete reason: were add a field, the + of a monoid would be a projection out of the monoid record, a different term from the + of the semigroup underneath, and every rewrite would have to be taught they are the same. As parameters, all layers share literally the same +.

Note the :: where a record field would have :. It declares the field to be an instance in its own right, so having a Monoid M in scope automatically puts a Semigroup M in scope, and a proof about semigroups applies with nothing restated. This is how the structures stack without repeating laws.

The module wrapper is only about names: inside Module Monoid, the field semigroup is in full Monoid.semigroup, so the prefix lives in the module path rather than in names like monoid_semigroup. The closing Export Monoid puts the short names in scope.

Rewriting needs permission

Choosing == freely has a price. If == were Coq’s built-in equality, replacing equals by equals anywhere would be automatic. With a chosen relation it is not: from a == b you may not conclude f a == f b unless someone has proved that f respects the relation. A function that does is called a setoid morphism, and the proof obligation is written with Coq’s standard Proper:

    neg_proper       :: Proper (equ ==> equ) neg;

Read equ ==> equ as “equal inputs to equal outputs”. Group carries this for negation, Magma carries the two-argument version for the operation, and together they are what let a chain rewrite inside a subterm. When you see a Proper field in a structure, that is all it is: the licence to rewrite under that operation.

One more line appears in every structure:

  Hint Mode Group ! - - - - : typeclass_instances.

It says when instance search may go looking for a group. The ! marks the carrier: it must already be a known type. Without that, a search for Group ?G with the carrier unknown can match a parametric instance — the pointwise structure on functions X -> M, say, whose carrier is itself a function type — and then match it again inside itself, forever. The - positions mark arguments that may still be unknown; finding those is the search’s job.

Chains

Proofs in this series are written as chains of equalities, one law per step:

    calc b
      == (0 + b)          { left_identity  }
      == ((- a + a) + b)  { left_inverse }
      == (- a + (a + b))  { associative }

which is meant to read like the blackboard line it transcribes. calc is not a Coq feature; it is a tactic notation defined in Lib/Calc.v, and the expansion is small enough to state exactly. The written endpoints are unified against the goal, each step becomes a transitivity through the intermediate term, and each { } is discharged by trying its justification six ways:

Ltac calc_by r :=
  first [ now rewrite r
        | now rewrite <- r
        | now apply r
        | now (symmetry; apply r)
        | now exact r
        | now (symmetry; exact r) ].

That is why a step can cite a law without saying which direction it is used in. It also explains two rules of thumb the posts obey: each term in a chain needs its own parentheses, because the slot is a whole term; and a term nothing else pins down needs an ascription, as in (0 : G), since the carrier is what tells search which 0 is meant. Chains stop at seven steps — beyond that, name the intermediate object and start a second chain. There is a post on what a calc proof compiles to for the longer version of this story.

What to expect from here on

That is the whole vocabulary. In the posts that follow, a structure is a class whose fields are laws drawn from the catalogue; a theorem is a chain; == is whatever equality the carrier chose; and the Proper and Hint Mode lines are plumbing you can now read past. Where a post shows Coq that is not one of these devices, it will say what the device is and why the mathematics needed it.
