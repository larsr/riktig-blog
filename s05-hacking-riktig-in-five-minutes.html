Hacking on riktig in five minutes: a lemma with no carrier, then a determinant

Everything in this post is one checked-in file, Examples/GettingStarted.v, rebuilt with the tree. It is in two halves, because using the library is two activities. In the first you state and prove something over a structure — a set of operations together with the laws they obey — and no type is ever named. In the second you name a type, and Coq assembles the structure over it for you, at which point things compute.

Getting a toolchain

Coq 8.20, coq-lsp matched to that version, GHC for the extracted Haskell, and an editor that speaks to all three. The repository carries a description of that environment, and VS Code builds it:

git clone git@git.ri.se:lars.rasmusson/riktig.git
code riktig            # open the folder in VS Code

VS Code notices .devcontainer/ and offers “Reopen in Container”. The first launch builds the image; later ones take seconds. Inside, make builds the theories, opening any theories/*.v file gives live proof goals through ejgallego.coq-lsp, and every terminal is already in the project’s Nix shell — the toolchain is pinned by flake.nix and flake.lock, so a proof that checks in one container checks in every other. A Docker volume named riktig-nix-store is mounted at /nix, so rebuilding the container does not re-download the toolchain. Without VS Code, .devcontainer/dev.sh does the same over plain Docker: dev.sh build compiles the theories, dev.sh shell gives an interactive one.

Half one: a proof that names no type

Two import lines put five theories in scope:

From Riktig.Structure Require Import Basis.
From Riktig.Theory Require Import InnerProductSpace InnerGeometry LinearMap.

A section opens by asking for the structure it works over. The binder below says: let F be a field of scalars, V any type of vectors over it, with the four vector-space laws available.

Section AbstractVectors.
  Context {F V : Type} `{VV : VectorSpace F V}.

F and V are variables. Nothing in the section can mention how a vector is stored, because there is nothing to mention. What the binder does bring is notation — + for addition, - v for negation, *: for scaling a vector by a scalar, == for the equality of the type at hand — and the names of the laws.

Here is a small regrouping. On the blackboard,

a(u−v)+bv=au+(b−a)v,a(u - v) + bv \;=\; au + (b - a)v,

reached in four steps — distribute the scaling over the difference, move the subtracted term to the end, reassociate, collect the two scalings of vv:

a(u−v)+bv=(au−av)+bv=(au+bv)−av=au+(bv−av)=au+(b−a)v.a(u-v)+bv \;=\; (au - av) + bv \;=\; (au + bv) - av \;=\; au + (bv - av) \;=\; au + (b-a)v.

In Coq, with u + - v for the difference — the structure has one addition and a negation, and subtraction is their composite:

  Lemma scale_regroup : forall (a b : F) (u v : V),
    a *: (u + - v) + b *: v == a *: u + (b + - a) *: v.
  Proof.
    intros a b u v.
    calc (a *: (u + - v) + b *: v)
      == ((a *: u + - (a *: v)) + b *: v)  { scale_sub }
      == ((a *: u + b *: v) + - (a *: v))  { add_swap_r }
      == (a *: u + (b *: v + - (a *: v)))  { associative }
      == (a *: u + (b + - a) *: v)         { sub_scale }.
  Qed.

A calc chain writes every intermediate term out and names, in braces, the one law that gets from the previous line to this one. The four justifications are general names, each a theorem or a law class of its own: scale_sub and sub_scale distribute a scaling over a difference (Theory/VectorSpace.v), add_swap_r is the abelian-group reshuffle (a + b) + c == (a + c) + b (Theory/AbGroup.v), and associative is the law class in Props.v that every associative operation in the library instantiates. None of them mentions a type.

Orthogonality, in the same style

An inner product ⟪ u , v ⟫ is a symmetric form, linear in each argument, and norm2 is the squared length ⟪ u , u ⟫. Squared, because a square root would need an order on the scalars and a completeness assumption, and none of the facts below need either.

Theory/InnerGeometry.v proves Pythagoras once, over any inner product space, where orthogonal u v abbreviates ⟪ u , v ⟫ == 0:

  Theorem pythagoras : forall u v : V,
    orthogonal u v -> norm2 (u + v) == norm2 u + norm2 v.

One consequence is that the two diagonals of a rectangle have the same length. If u⟂vu \perp v then

∥u−v∥2=∥u∥2+∥−v∥2=∥u∥2+∥v∥2=∥u+v∥2,\|u-v\|^2 = \|u\|^2 + \|{-v}\|^2 = \|u\|^2 + \|v\|^2 = \|u+v\|^2,

Pythagoras at each end and norm2_neg — negating a vector does not change its squared length — in the middle:

  Theorem norm2_orthogonal_diagonals : forall u v : V,
    ⟪ u , v ⟫ == 0 -> norm2 (u + - v) == norm2 (u + v).
  Proof.
    intros u v Huv.
    calc (norm2 (u + - v))
      == (norm2 u + norm2 (- v))
           { (pythagoras u (- v) (orthogonal_neg_r u v Huv)) }
      == (norm2 u + norm2 v)
           { norm2_neg }
      == (norm2 (u + v))
           { (pythagoras u v (orthogonal_def u v Huv)) }.
  Qed.

The first step needs u⟂−vu \perp -v, and ⟨u,−v⟩=−⟨u,v⟩=−0=0\langle u, -v\rangle = -\langle u,v\rangle = -0 = 0 gives it, one law per step again:

  Lemma orthogonal_neg_r : forall u v : V,
    ⟪ u , v ⟫ == 0 -> orthogonal u (- v).
  Proof.
    intros u v Huv.
    apply orthogonal_def.
    calc (⟪ u , - v ⟫)
      == (- ⟪ u , v ⟫)  { inner_right_neg }
      == (- (0 : F))    { Huv }
      == (0 : F)        { neg_zero }.
  Qed.

Coordinates, with a basis in the binder

A basis in this library is a pair of inverse maps: a family of vectors indexed by a finite type I, and a linear map sending a vector to its coordinates. Basis.reconstruction is one half of that inverse pair — a vector is the combination lincomb of the family with its own coordinates — and lincomb_proper says the combination only reads the coefficients, so equal coefficients give equal combinations. From the two, coordinates determine the vector:

u=∑ici(u)ei=∑ici(v)ei=v.u = \sum_i c_i(u)\, e_i = \sum_i c_i(v)\, e_i = v.

  Context {n : nat} {I F V : Type} `{B : Basis n I F V}.
  Theorem coords_determine : forall u v : V,
    (forall i : I, Basis.coords B u i == Basis.coords B v i) -> u == v.
  Proof.
    intros u v Hc.
    calc u
      == (lincomb (Basis.vec B) (Basis.coords B u))
           { (Basis.reconstruction B u) }
      == (lincomb (Basis.vec B) (Basis.coords B v))
           { (lincomb_proper (Basis.vec B) (Basis.coords B u)
                (Basis.coords B v) Hc) }
      == v
           { (Basis.reconstruction B v) }.
  Qed.

Three steps: expand u, swap coefficients, contract to v. The index type I is a variable too — the basis is n-dimensional because I has n elements, not because anything is a tuple.

Half two: name a type, and it computes

One import line brings the implementations:

From Riktig.Impl Require Import Fin Det.

Impl/Det.v exports Impl/Matrix.v, which exports Impl/FinVec.v and Impl/Qf.v. Between them they register the rationals as a field, the functions Fin.t n -> F as a vector space with an inner product, and square matrices as a ring. Registered means: Coq finds them by search, and the underscore below is a request to do so.

Example q_is_a_field : Field Q := _.
Example q4_is_a_vector_space : VectorSpace Q (Fin.t 4 -> Q) := _.
Example q4_has_an_inner_product : InnerProductSpace Q (Fin.t 4 -> Q) := _.
Example q4_matrices_form_a_ring : Ring (Matrix 4 4 Q) := _.

Four structures over three carriers, none written by hand. Q is the standard library’s rationals, a pair of integers compared by cross-multiplication, so 1#2 and 2#4 are different terms and equal scalars — the reason the library’s == is a chosen equivalence relation per type rather than Coq’s built-in =.

A vector in Fin.t 4 -> Q is a function from a four-element index type, and a matrix is a function of two such indices, so writing one down means writing a function. fin_to_nat turns an index into its position:

Definition vec4 (a b c d : Q) : Fin.t 4 -> Q :=
  fun i => match fin_to_nat i with
           | O => a
           | 1%nat => b
           | 2%nat => c
           | _ => d
           end.
Definition u4 : Fin.t 4 -> Q := vec4 (1#1) (2#1) (3#1) (4#1).
Definition v4 : Fin.t 4 -> Q := vec4 (2#1) (-1#1) (4#1) (-3#1).

The inner product on Fin.t n -> F is ∑iuivi\sum_i u_i v_i, so over Q it runs. Qred puts a rational in lowest terms; each line below is an equation between closed terms, proved by eq_refl — that is, checked by the kernel evaluating both sides, so the build checks the numbers:

Example inner_u4_v4 : Qred ⟪ u4 , v4 ⟫ = 0 # 1 := eq_refl.
Example inner_u4_u4 : Qred ⟪ u4 , u4 ⟫ = 30 # 1 := eq_refl.
Example inner_v4_v4 : Qred ⟪ v4 , v4 ⟫ = 30 # 1 := eq_refl.
Example norm2_sum_u4_v4 : Qred (norm2 (u4 + v4)) = 60 # 1 := eq_refl.
Example norm2_diff_u4_v4 : Qred (norm2 (u4 + - v4)) = 60 # 1 := eq_refl.

1⋅2+2⋅(−1)+3⋅4+4⋅(−3)=01 \cdot 2 + 2 \cdot (-1) + 3 \cdot 4 + 4 \cdot (-3) = 0, so the two vectors are orthogonal; both have squared length 3030; and both diagonals come out 6060. Those last two numbers are what the abstract theorems predict, and the theorems apply here as they stand — the proof terms are the general ones, nothing is re-proved at Q:

Example u4_orth_v4 : ⟪ u4 , v4 ⟫ == 0.
Proof. vm_compute. reflexivity. Qed.
Example pythagoras_at_Q4 :
  norm2 (u4 + v4) == norm2 u4 + norm2 v4 :=
  pythagoras u4 v4 (orthogonal_def u4 v4 u4_orth_v4).

Example diagonals_at_Q4 :
  norm2 (u4 + - v4) == norm2 (u4 + v4) :=
  norm2_orthogonal_diagonals u4 v4 u4_orth_v4.

A determinant that runs

detM is the cofactor expansion along the first column, written for an arbitrary field. Give it a matrix over Q and it is a program. Two 4×44 \times 4 matrices, one whose rows count 11 to 1616 and one with 22 on the diagonal and 1/31/3 everywhere else:

Definition counting : Matrix 4 4 Q :=
  mat4 (vec4 (1#1) (2#1) (3#1) (4#1))
       (vec4 (5#1) (6#1) (7#1) (8#1))
       (vec4 (9#1) (10#1) (11#1) (12#1))
       (vec4 (13#1) (14#1) (15#1) (16#1)).

Definition two_on_the_diagonal : Matrix 4 4 Q :=
  mat4 (vec4 (2#1) (1#3) (1#3) (1#3))
       (vec4 (1#3) (2#1) (1#3) (1#3))
       (vec4 (1#3) (1#3) (2#1) (1#3))
       (vec4 (1#3) (1#3) (1#3) (2#1)).
Example det_counting : Qred (detM counting) = 0 # 1 := eq_refl.
Example det_two_on_the_diagonal :
  Qred (detM two_on_the_diagonal) = 125 # 9 := eq_refl.

The first is 00: consecutive rows differ by the same vector (4,4,4,4)(4,4,4,4), so all four rows lie in the plane spanned by the first row and that difference, and four vectors in a plane are dependent. The second is exact rather than rounded — 125/9=3⋅(5/3)3125/9 = 3 \cdot (5/3)^3, which is what the eigenvalues give: the all-ones vector has eigenvalue 2+3⋅13=32 + 3 \cdot \tfrac13 = 3, and the 33-dimensional space orthogonal to it has eigenvalue 2−13=532 - \tfrac13 = \tfrac53. Nothing rounds, because the entries are pairs of integers.

The standard basis of Fin.t 4 -> Q is in Impl/FinVecBasis.v, and coordinates in it compute as well:

Definition B4 : Basis 4 (Fin.t 4) Q (Fin.t 4 -> Q) := FinVec_Basis 4.
Example coords_of_u4 :
  Qred (Basis.coords B4 u4 (Fin.FS Fin.F1)) = 2 # 1 := eq_refl.

Coordinates go one way, the linear combination goes back, and over Q the round trip is a number the build checks:

Example reconstruct_u4_at_1 :
  Qred (lincomb (Basis.vec B4) (Basis.coords B4 u4) (Fin.FS Fin.F1))
  = 2 # 1 := eq_refl.
Example coords_determine_at_Q4 : forall u v : Fin.t 4 -> Q,
  (forall i : Fin.t 4, Basis.coords B4 u i == Basis.coords B4 v i) -> u == v :=
  coords_determine (B := B4).

The last line is the abstract theorem again, its basis argument filled in with this one.

The 2 above is worth a sentence, because 0 used to come out of it. Fin.t 4 -> Q carries a pointwise additive monoid and a pointwise multiplicative one, both built by the same instance from the two monoids on Q, and lincomb is a fold over one of them. Which one is not visible in HasLincomb I F V: the class names the index, the scalars and the vectors, and no operation. So an instance for it that asks for a Monoid V hands search a free choice, and search took the multiplicative reading — under which the sum above is a product with a zero factor. The instance now asks for Zero V and HasAdd V, which is all the fold uses, and those two goals have one solution each at this carrier. The Monoid stays one level up, on the instance of the equation lincomb b c == bigopI (fun i => c i *: b i), where the operation is a parameter of the class and shows up in the type.

Where things live

Three directories, one job each, one import prefix each.

  • Structure/ — the classes and the laws they bundle. VectorSpace in Structure/VectorSpace.v is four laws over a scalar action; Basis in Structure/Basis.v is two round-trip equations. Nothing here is proved; these are the definitions. From Riktig.Structure Require Import Basis.
  • Theory/ — what follows from those laws, over anonymous carriers. Theory/InnerGeometry.v has Pythagoras, Cauchy–Schwarz and projections; Theory/Basis.v has the linear-combination lemmas. From Riktig.Theory Require Import InnerGeometry.
  • Impl/ — a type to compute with, and its instances. Impl/Qf.v registers Q, Impl/FinVec.v the space Fin.t n -> F, Impl/Matrix.v the matrix ring, Impl/Det.v the determinant. From Riktig.Impl Require Import Det.

Require Export passes a file’s own imports on to whoever asks for it, Require Import keeps them private, which is why two lines sufficed above and why Theory/InnerProductSpace.v still had to be named: Theory/InnerGeometry.v imports it without exporting it.

The split is what makes the first half of this post possible. A law that mentioned Fin.t or Q would make those types part of the meaning of the structure, and a proof about them would not survive a change of representation. Instead the operations are class parameters, the laws are equations, and a concrete type shows up in Impl/ as an instance — so pythagoras is proved once and holds for the rationals, for the reals, for polynomials, and for whatever gets registered next.
