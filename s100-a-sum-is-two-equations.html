A sum is two equations, not a fold

Write down what it means to add up a list of numbers. Most people reach for a recursion:

Σ([])=0,Σ(x:xs)=x+Σ(xs)\Sigma(\,[\,]\,) = 0, \qquad \Sigma(x : xs) = x + \Sigma(xs)

Read those two lines as a program and you get one particular function: it walks the list from the right, opening the whole list before adding anything. Read them as equations and you get something much larger — the set of all functions that satisfy them. The right-to-left walk is one. So is a left-to-right walk that carries a running total, and a balanced tree that halves the list and adds the halves, and a circuit that adds four numbers per clock tick.

The distinction sounds pedantic until you prove something. Suppose you want the fact that a sum splits at a concatenation:

Σ(l1++l2)=Σ(l1)+Σ(l2)\Sigma(l_1 \mathbin{+\!\!+} l_2) = \Sigma(l_1) + \Sigma(l_2)

If your Σ\Sigma is the right-to-left program, you can prove this by induction, and what you have proved is a fact about that program. Hand someone the left-to-right sum and your theorem says nothing about it, even though it is just as true there — because your theorem’s subject was a particular recursion, not addition-over-a-list. Every law you prove has to be proved again for each new way of summing.

Making the equations the definition

Nothing forces that. The two equations can be the definition, with the operation left open. In Coq that is a type class: a parameter for the operation, and the equations as its fields.

  Class BigOp (M : Type) {Me : EqRel M} {Mz : Zero M} {Ma : HasAdd M}
      (bigop_list : forall J : Type, (J -> M) -> list J -> M) := {
    bigop_list_nil : forall (J : Type) (f : J -> M),
      bigop_list J f nil == 0;
    bigop_list_cons : forall (J : Type) (f : J -> M) (j : J) (l : list J),
      bigop_list J f (j :: l) == f j + bigop_list J f l;
  }.

Read it back into English: bigop_list takes a family f — a function from index to value — and a list of indices, and returns a value; the empty list gives 0, and a list with head j gives f j added to the sum of the rest. M is the carrier being summed in, and == is its equality, which need not be Coq’s built-in one. HasAdd M and Zero M say that M has the + and 0 the two equations mention.

The operation is a parameter of the class, in round brackets, not a field. That is the whole design decision. A field would mean “there is a distinguished sum, and here are its laws”; a parameter means “here is what it takes for something to be a sum”, and different things can qualify.

A law, proved once

Here is the concatenation fact, proved from the two equations and nothing else. In the file this sits in a section that has fixed a carrier M with its monoid laws and has taken bigop_list with its BigOp instance as parameters, so bigop_list here is any lawful sum.

Σf([]++l2)=0+Σf(l2)left identity=Σf([])+Σf(l2)the nil equation \begin{aligned} \Sigma_f([\,] \mathbin{+\!\!+} l_2) &= 0 + \Sigma_f(l_2) && \text{left identity} \\ &= \Sigma_f([\,]) + \Sigma_f(l_2) && \text{the nil equation} \end{aligned}

and for a non-empty left list, writing j:l1j : l_1 for its head and tail,

Σf((j:l1)++l2)=f(j)+Σf(l1++l2)the cons equation=f(j)+(Σf(l1)+Σf(l2))induction hypothesis=(f(j)+Σf(l1))+Σf(l2)associativity=Σf(j:l1)+Σf(l2)the cons equation \begin{aligned} \Sigma_f((j : l_1) \mathbin{+\!\!+} l_2) &= f(j) + \Sigma_f(l_1 \mathbin{+\!\!+} l_2) && \text{the cons equation} \\ &= f(j) + (\Sigma_f(l_1) + \Sigma_f(l_2)) && \text{induction hypothesis} \\ &= (f(j) + \Sigma_f(l_1)) + \Sigma_f(l_2) && \text{associativity} \\ &= \Sigma_f(j : l_1) + \Sigma_f(l_2) && \text{the cons equation} \end{aligned}

The Coq is the same two chains:

  Lemma bigop_list_append : forall {J : Type} (f : J -> M) (l1 l2 : list J),
    bigop_list f (l1 ++ l2) == bigop_list f l1 + bigop_list f l2.
  Proof.
    intros J f l1 l2; induction l1 as [| a l1 IH].
    - calc (bigop_list f (nil ++ l2))
        == (0 + bigop_list f l2)                    { left_identity }
        == (bigop_list f nil + bigop_list f l2)     { (bigop_list_nil f) }.
    - calc (bigop_list f ((a :: l1) ++ l2))
        == (f a + bigop_list f (l1 ++ l2))             { (bigop_list_cons f a (l1 ++ l2)) }
        == (f a + (bigop_list f l1 + bigop_list f l2)) { IH }
        == ((f a + bigop_list f l1) + bigop_list f l2) { associative }
        == (bigop_list f (a :: l1) + bigop_list f l2)  { (bigop_list_cons f a l1) }.
  Qed.

calc is a small tactic for writing a chain of equalities the way you would on a blackboard: each == line is the next expression, and the { ... } after it is the law that justifies that one step. The induction is on the left list, and the base case is not reflexivity — bigop_list f nil is not computed to 0 here, because there is nothing to compute. It is turned into 0 by citing the nil equation, which is the only thing known about it.

That is the whole difference. The proof never mentions a recursion, so it is not about one.

Two sums that satisfy it

An abstraction with one instance is a rename. Here are two.

The first is the obvious one, the right fold:

Definition bigop_list {M : Type} {Mz : Zero M} {Ma : HasAdd M}
    {J : Type} (f : J -> M) (l : list J) : M :=
  fold_right (fun j acc => f j + acc) 0 l.

Its two equations hold by computation — fold_right is the recursion the equations describe, so both sides of each equation are the same term:

Instance BigOp_fold {M : Type} {Me : EqRel M} {Mz : Zero M} {Ma : HasAdd M}
    {MR : Reflexive (@equ M Me)} : BigOp M (@bigop_list M _ _).
Proof.
  split; intros; reflexivity.
Qed.

The second walks the other way, carrying a running total:

  Fixpoint bigop_go {J : Type} (a : M) (f : J -> M) (l : list J) : M :=
    match l with
    | nil => a
    | j :: l' => bigop_go (a + f j) f l'
    end.

  Definition bigop_acc {J : Type} (f : J -> M) (l : list J) : M :=
    bigop_go 0 f l.

For this one the equations are not free. The empty list still gives 0 on the nose, but the cons equation says

Σ(j:l)=f(j)+Σ(l)\Sigma(j : l) = f(j) + \Sigma(l)

while the program produces go(0+f(j),l)\mathrm{go}(0 + f(j), l) — the head has been added into the accumulator, and everything in ll gets added after it. Getting from one to the other means pulling the accumulator back out in front, and that is a small induction of its own:

go(a,l)=a+go(0,l)\mathrm{go}(a, l) = a + \mathrm{go}(0, l)

With that lemma the cons equation is four steps:

Σacc(j:l)=go(0+f(j),l)unfolding=(0+f(j))+go(0,l)the accumulator lemma=f(j)+go(0,l)left identity=f(j)+Σacc(l)unfolding \begin{aligned} \Sigma_{\mathrm{acc}}(j : l) &= \mathrm{go}(0 + f(j),\, l) && \text{unfolding} \\ &= (0 + f(j)) + \mathrm{go}(0, l) && \text{the accumulator lemma} \\ &= f(j) + \mathrm{go}(0, l) && \text{left identity} \\ &= f(j) + \Sigma_{\mathrm{acc}}(l) && \text{unfolding} \end{aligned} 

  #[export] Instance BigOp_acc : BigOp M (@bigop_acc).
  Proof.
    split.
    - intros J f. exact (reflexivity (0 : M)).
    - intros J f j l.
      calc (bigop_acc f (j :: l))
        == (bigop_go ((0 : M) + f j) f l)
             { (reflexivity (bigop_go ((0 : M) + f j) f l)) }
        == (((0 : M) + f j) + bigop_go 0 f l)
             { (bigop_go_shift f l ((0 : M) + f j)) }
        == (f j + bigop_go 0 f l)
             { (op_proper _ _ (left_identity (f j)) _ _
                 (reflexivity (bigop_go 0 f l))) }
        == (f j + bigop_acc f l)
             { (reflexivity (f j + bigop_go 0 f l)) }.
  Qed.

The two reflexivity steps are the two unfoldings; bigop_go_shift is the accumulator lemma; op_proper is the fact that + respects ==, used to rewrite inside the right-hand summand.

Notice what the accumulator sum needed that the fold did not: associativity. The accumulator was added first and has to be moved past everything the walk adds after it. So the two equations really are a constraint — they are not satisfied by any old traversal.

What the second instance gets for free

Everything. The concatenation law was proved about bigop_list the parameter, so it applies to the accumulator sum by citation:

Example acc_append (M : Type) `{Monoid M} (J : Type) (f : J -> M)
    (l1 l2 : list J) :
  bigop_acc f (l1 ++ l2) == bigop_acc f l1 + bigop_acc f l2 :=
  bigop_list_append (bigop_list := @bigop_acc M _ _) f l1 l2.

There is no proof there — the body is the earlier lemma, with the operation supplied by name. The same holds for every other law proved from the two equations: extensionality, the sum of a sum, the interchange ∑i∑j=∑j∑i\sum_i \sum_j = \sum_j \sum_i, the collapse of a sum against a Kronecker delta.

And it runs. Adding 1+2+3+41 + 2 + 3 + 4 over the integers, left to right where the fold goes right to left:

Example acc_computes_on_Z :
  bigop_acc (fun i : Z => i) (1 :: 2 :: 3 :: 4 :: nil)%Z = 10%Z.
Proof. reflexivity. Qed.

The mistake this prevents

The reason to care is not tidiness. It is that a law which names one sum is a law no other sum can satisfy, and that is easy to do by accident — you write the specification of something else, a matrix product say, and reach for the summation you have:

    mat_mul_def : forall {I K : Type} (A : I -> J -> F) (B : J -> K -> F)
                        (i : I) (k : K),
      mat_mul A B i k == bigop_list (fun j => A i j * B j k) enum.

Here bigop_list is a parameter of the class this equation belongs to, carried along with its BigOp laws, exactly as above. Had it been the fold instead, this would say “entry (i,k)(i,k) is what this recursion computes” — and a matrix product built on any other summation, however correct, would fail to be a matrix product by this definition. Nothing proved from it would transfer, which is the opposite of what a specification is for.

The rule of thumb that falls out: when a specification needs an operation it does not itself define, take it as a parameter with its laws attached, and never name a term that computes. The test is whether a second implementation can satisfy what you wrote. If it cannot, you have specified an implementation.
